# Renderer run grouping — frozen baseline

Measured BEFORE any grouping work, so the same harness can prove what changed. No
latency thresholds are asserted here; these are raw numbers for comparing equivalent
runs.

Harness: `examples/vite/public/bench/renderer-baseline.js`, committed and served by the
Vite demo. Numbers below were taken by running its measurement steps against a live
editor instance (`window.__docxAdapterEditor`).

## Size — the numbers grouping is meant to move

| Metric | Comprehensive (`sample.docx`) | Large styled text |
| --- | --- | --- |
| Pages | 10 | 23 |
| Layout text items | 2,331 | 11,168 |
| Glyph runs | 2,287 | 11,166 |
| Painted text elements | 2,287 | 11,166 |
| Total DOM nodes under `.ep-one-surface__pages` | 3,913 | 11,235 |

Painted text elements track glyph runs 1:1 today — one absolutely positioned element per
word-or-style slice. That is the ratio the change targets.

## Timing

| Operation | Comprehensive | Large styled text |
| --- | --- | --- |
| `load()` (parse + layout, synchronous) | 315 ms | 1,134 ms |
| Selection-only click (dispatch → return) | 41.7 ms | 674.7 ms |
| `exec(toggleMark)` with a collapsed caret | 1.2 ms (`changed: false`) | — |
| `exec(toggleMark)` over a selection | — | 1,205 ms |

Scaling is SUPERLINEAR in the thing grouping reduces: DOM nodes grow 2.9x between the
two fixtures while a selection-only click grows 16x.

## DOM identity on selection-only frames — already preserved

Measured by tagging each live page element with a JavaScript EXPANDO (not an attribute,
which would be copied onto a rebuilt node and report false success), clicking, then
checking the same objects are still mounted.

| Fixture | Page-content identity | Nodes added | Nodes removed |
| --- | --- | --- | --- |
| Comprehensive | preserved | 1 | 0 |
| Large styled text | preserved | 1 | 0 |

**This corrects an assumption worth stating plainly:** the change's requirement 4 says a
selection-only frame must not recreate unchanged page content, and the DOM already meets
that — the single added node is the caret overlay. The 675 ms is therefore NOT DOM
teardown. It is React reconciling 11,166 elements plus the engine republishing the frame.
Memoizing page content will still help, but the win comes from skipping RECONCILIATION,
not from stopping DOM churn that is not happening. A "static page content" split measured
only by node identity would report success while changing nothing.

## Invariants to hold constant

Grouping must not move these. Both are computed from engine geometry rather than from
painted elements, so they stay comparable after elements are merged:

- **Wrapping signature** — every text run bucketed by rounded baseline `y` within a page,
  concatenated in `x` order. Same signature ⇒ the same words landed on the same lines.
- **Visible text hash** — the signature's text content, ordered.

Recorded via the harness's `invariants` block on each run rather than pasted here, since
they are hashes whose only use is equality against a later run.

## What the baseline already tells us about the work

1. Painted elements equal glyph runs exactly, so the element count is fully determined by
   how layout slices text. Grouping has to change the SLICING, not just the painting.
2. `TextItem` in `packages/engine-layout/src/display-item.ts` carries only `bold` and
   `italic`. The change's requirement 6 — the full basic-formatting matrix — is therefore
   a prerequisite for grouping, not a follow-up: a grouping key built from today's
   properties would merge runs that differ in underline, colour, size, or caps.
3. Selection-only cost is dominated by reconciliation over every painted element, which
   is why requirement 4 pairs with grouping rather than standing alone.
