## ADDED Requirements

### Requirement: The Vue adapter SHALL resolve exactly one copy of the engine

`@docx-editor.dev/vue` SHALL declare `@docx-editor.dev/core` as a required `peerDependency` and
as a `workspace:*` `devDependency`, and SHALL NOT declare it as a regular `dependency`. The
published bundle SHALL import the engine by bare specifier and SHALL NOT inline it.

The engine holds module-level state — the HarfBuzz shaper and its cache budget, the grapheme
boundary strategy, and layout caches keyed by object identity. Two copies in one tree do not
crash: they load the shaper twice, read a boundary configured on the other copy, and miss every
identity-keyed cache. A peer makes the package manager resolve one and say so at install when it
cannot.

#### Scenario: The manifest asks for the engine as a peer

- **WHEN** `packages/vue/package.json` is read
- **THEN** `peerDependencies['@docx-editor.dev/core']` is present and is not marked optional in
  `peerDependenciesMeta`
- **AND** `dependencies['@docx-editor.dev/core']` is absent
- **AND** `devDependencies['@docx-editor.dev/core']` is `workspace:*`, so this workspace builds
  and tests against the engine

#### Scenario: The build leaves the engine external

- **WHEN** the package is built and `dist/index.js` is read
- **THEN** it contains a bare import of `@docx-editor.dev/core` or one of its subpaths
- **AND** it contains no copy of the engine's module-level shaper setup

#### Scenario: A page running both packages gets one engine

- **WHEN** a host installs `@docx-editor.dev/vue`, `@docx-editor.dev/core` and
  `@docx-editor.dev/pro` at compatible versions
- **THEN** the package manager resolves a single `@docx-editor.dev/core`, and a pro module
  registered against the editor the Vue adapter created is the same engine that paints

### Requirement: The Vue package SHALL be publishable and installable

The manifest SHALL carry no `workspace:` specifier in a field a consumer resolves, SHALL NOT be
`private`, and SHALL declare an `exports` map whose subpaths match `@docx-editor.dev/react`
exactly. The build SHALL emit an esbuild metafile so the third-party notice generator has an
attribution path.

Published packages are one fixed group: a changeset declares one bump and the rest follow.

#### Scenario: The packed tarball installs

- **WHEN** `bun run check:consumer-install` runs over the packed tarballs
- **THEN** the Vue tarball installs without `EUNSUPPORTEDPROTOCOL`, and every dependency it
  names exists on the registry

#### Scenario: Subpath parity holds

- **WHEN** `bun run check:export-parity` compares the two adapters' `exports` maps
- **THEN** the subpath sets are identical with no exemption

#### Scenario: The notice generator has something to read

- **WHEN** `bun run build:packages && bun run notices:generate` runs
- **THEN** the Vue package emits `dist/metafile-*.json`, the generator reads it, and the run
  succeeds — an empty notice is the correct result when nothing is inlined, and a bundled
  dependency with no license text fails the run outright

### Requirement: The Vue adapter SHALL be built with the same toolchain contract as React

The package SHALL build with `tsup`, SHALL externalize `vue`, the engine, the i18n package,
`harfbuzzjs` and `emf-converter`, and SHALL author components as render-function TypeScript
(`defineComponent` + `h`) rather than single-file components.

`tsup` does not compile SFCs, `max-lines` is the only gate that catches an over-long file and it
counts `.ts` reliably, and the existing Vue components are already written this way.

#### Scenario: No SFC reaches the build

- **WHEN** `packages/vue/src` is walked
- **THEN** it contains no `.vue` file

#### Scenario: The package joins the build

- **WHEN** `bun run build:packages` runs
- **THEN** `@docx-editor.dev/vue` is built, its API Extractor snapshot is regenerated by
  `bun run api:extract`, and `bun run api:check` reports no drift

### Requirement: The Vue package SHALL be rebuilt greenfield, mirroring the React tree

`packages/vue/src` and `packages/vue/test` SHALL be removed before the rebuild starts, and
nothing SHALL be carried over. A paired export SHALL then live at the same relative path in both
adapters, differing only in file extension, and the Vue tree SHALL NOT contain a file with no
React counterpart.

`check:feature-parity` walks both trees and compares them file by file, so shared paths are what
make its report mean anything.

#### Scenario: The old tree is gone

- **WHEN** the removal commit lands
- **THEN** `packages/vue/src` holds only the unchanged stylesheet and an empty entry, and
  `packages/vue/test` is empty

#### Scenario: Every Vue source file has a React counterpart

- **WHEN** the two `src` trees are walked
- **THEN** every Vue file has a React file at the same relative path, modulo the file extension

#### Scenario: The feature-parity report is readable

- **WHEN** `bun run check:feature-parity` runs
- **THEN** its per-file comparison pairs real counterparts, and each remaining difference names a
  capability rather than a path mismatch

### Requirement: The pre-v2 React chrome SHALL be deprecated rather than paired

The pre-v2 shell chrome SHALL carry a `@deprecated` TSDoc tag naming its replacement and SHALL
NOT gain a Vue twin, and every parity gate SHALL read that tag from the API Extractor snapshot
and measure over the NON-DEPRECATED surface. The set is `Toolbar`, `ToolbarButton`,
`ToolbarGroup`, `ToolbarProps`, `TitleBar`, `MenuBar`, `DocumentName`, `Logo`, `TitleBarRight`,
`DocxEditorShell`, `PaginatedDocxEditorShell` and `PaginatedDocxEditorShellProps`.

The composition layer replaces every one of them — `DocxEditor.Toolbar`, `DocxEditor.Menu`, the
packaged `<DocxEditor>` — and nothing in `examples/` imports one. A Vue twin would be chrome
built with a removal date already on it. Reading the tag out of the snapshot is a fact about the
code; an exemption list is not, and the divergence file this change deletes is what an exemption
list becomes.

#### Scenario: The tag reaches the snapshot

- **WHEN** the React API Extractor snapshot is regenerated
- **THEN** each of those symbols is marked deprecated in the report, with its replacement named

#### Scenario: Parity ignores them

- **WHEN** `bun run check:export-parity` runs
- **THEN** a deprecated React export with no Vue twin does not fail the gate, and no allowlist
  entry was needed to achieve that

#### Scenario: A non-deprecated export still fails

- **WHEN** a React export that carries no `@deprecated` tag has no Vue twin
- **THEN** the gate fails

#### Scenario: The props-driven primitives are not in the set

- **WHEN** `HorizontalRuler`, `VerticalRuler`, `DocumentOutline`, `PageIndicator` and
  `PaginatedDocxEditor` are checked
- **THEN** none is deprecated and each has a Vue twin, because the v2 context-fed parts wrap
  them

### Requirement: The parity gates SHALL run in CI with no exemptions

`check:parity-contract` SHALL be restored to `.github/workflows/ci.yml`, and
`check:export-parity` SHALL pass with NO documented divergence: every non-deprecated React export
has a Vue export of the same name, and every Vue export has a React one.

`openspec/changes/typed-ooxml-paragraph-editor/notes/intentional-export-divergence.md` is
deleted, and the opt-out load is removed from `check-export-parity.mjs` so the gate has nothing
to forgive.

#### Scenario: Named-export parity holds at 100% of the live surface

- **WHEN** `bun run check:export-parity` runs
- **THEN** the two adapters' non-deprecated named-export sets are identical
- **AND** no divergence file is read, because none exists

#### Scenario: The parity contract classifies every prop

- **WHEN** `bun run check:parity-contract` runs against the two committed API snapshots
- **THEN** every member of `DocxEditorProps` and `DocxEditorRef` on either adapter is classified,
  and no `deferredInVue` entry has shipped in Vue without being moved to `paired`

#### Scenario: The Vue-only pre-v2 exports are gone

- **WHEN** the Vue entry is read
- **THEN** it exports no `DocxEditorSidebar`, `DEFERRED_DIALOGS`, `SidebarPanel`,
  `DeferredDialogId`, `DocxEditorTitleBar`, `DocxEditorShellProps`, `PageIndicatorProps`,
  `runSave` or `toolbarCommandStates`

### Requirement: The Nuxt module SHALL import only subpaths that exist

`packages/nuxt/src/module.ts` SHALL auto-import composables from the Vue package ROOT, SHALL
point at the engine's stylesheet rather than a Vue-owned one, and SHALL list only composables
the Vue entry exports.

Subpath parity is strict and React has one entry, so Vue keeps one. The module currently names
`@docx-editor.dev/vue/composables` and `@docx-editor.dev/vue/styles.css`, neither of which
exists, and auto-imports fifteen pre-v2 composable names.

#### Scenario: Every auto-imported name resolves

- **WHEN** the module's auto-import list is compared with the Vue entry's named exports
- **THEN** every listed name is exported

#### Scenario: The component stays client-only

- **WHEN** a Nuxt app server-renders a page containing the editor
- **THEN** the component renders its placeholder, the server run creates no editor, and
  hydration mounts the real one

### Requirement: Dead lint overrides SHALL be removed

`eslint.config.js` SHALL carry no `max-lines` override naming a path that does not exist.

Four globs name three pre-v2 Vue files: `packages/vue/src/components/DocxEditor.vue`,
`packages/vue/src/composables/useDocxEditor.ts` and `packages/vue/src/components/Toolbar.vue`.
A cap that matches nothing is a cap that silently stops applying when a file with that name
comes back.

#### Scenario: Every override matches a file

- **WHEN** each `files` glob in `eslint.config.js` is resolved against the working tree
- **THEN** every glob naming a specific file matches an existing file
