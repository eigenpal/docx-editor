This package is the engine. It reads a `.docx` into a canonical document tree, lays that tree out into pages, paints them, and writes the tree back to OOXML. It has no framework dependency and no UI.

Most apps never import it directly: `@docx-editor.dev/react` carries it. Import it when you are writing your own adapter, or when you need the contract types to type a function signature.

```bash
npm install @docx-editor.dev/core
```

## Entry points

The root is the entry point for typical editor creation and typing: create an editor over bytes, the contract it implements, fonts, and the chrome registry.
See the [chrome slot reference](/docs/2.x/guides/chrome-slots) for the complete
registry vocabulary and its React and Vue toolbar parts.

```ts
import { createDocxEditor, loadFonts, WORD_DEFAULT_FONT } from '@docx-editor.dev/core';
import type { Editor, EditorSnapshot } from '@docx-editor.dev/core';
```

Import a subpath when you need the canonical tree, the layout pass, or the paint step directly.

| Subpath                   | Contents                                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `.`                       | Create an editor, the `Editor` contract, fonts, the chrome registry, the document model types.                              |
| `./editor`                | Everything the root re-exports, plus the paginated surface, ruler geometry, and module resolution.                          |
| `./contracts/editor`      | `Editor`, `EditorCommand`, `EditorQuery`, `EditorSnapshot`, `DocumentSource`, `PageSetup`, the contract an adapter renders. |
| `./contracts/document`    | The document-level edit and query vocabulary.                                                                               |
| `./contracts/types`       | Document model types.                                                                                                       |
| `./contracts/modules`     | `EditorModule`, the shape [`@docx-editor.dev/pro`](/docs/2.x/pro) implements.                                               |
| `./contracts/interaction` | Semantic addressing (`SemanticTarget`) and the `InteractionOutcome` that an attempt returns.                                |
| `./store`                 | The canonical tree and its transactional store.                                                                             |
| `./layout`                | The DOM-free layout pass.                                                                                                   |
| `./output`                | Paint: turning a laid-out document into page DOM, and the selection overlay over it.                                        |
| `./automation`            | The document object model behind [`@docx-editor.dev/editor-api`](/docs/2.x/editor-api).                                     |
| `./styles/editor.css`     | The editor stylesheet. The packaged chrome and your own chrome both use it.                                                 |

Prefer the root import. Use `./editor` only when you build an adapter and need
surface internals (the paginated surface, ruler geometry, module resolution).

## The contract

`Editor` is the whole public surface an adapter uses. Call `exec` for commands. Call `query` and `snapshot` for reads:

```ts
import type { Editor, EditorSnapshot } from '@docx-editor.dev/core/contracts/editor';

function pageLabel(editor: Editor): string {
  const snapshot: EditorSnapshot = editor.snapshot();
  return `${snapshot.page.current} / ${snapshot.page.total}`;
}
```

`snapshot()` is version-cached: it returns the same reference until editor state changes, and its sub-objects are reference-stable. That is what makes `useSyncExternalStore` (and therefore [`useEditorState`](/docs/2.x/react/hooks)) correct without a deep compare on every store notification.

### Group one gesture into one undo step

If your app applies a value on every slider movement or color-picker input,
group those writes into one user gesture. Each value renders and replicates
immediately. One Undo restores the formatting before the gesture, including a
mixed selection; Redo restores the final value.

In React or Vue, start with `useEditorValueCommand` and `useHistoryGroup`:
[React integration](/docs/2.x/react/hooks#usehistorygroup) ·
[Vue integration](/docs/2.x/vue/composables#usehistorygroup).
If your app owns the DOM directly, use `bindHistoryGroup` from the core package.
You keep using `editor.exec` to apply commands.

This range control changes font size in points. The command takes half-points:

```ts
import { bindHistoryGroup, type Editor } from '@docx-editor.dev/core';

function mountFontSize(editor: Editor, slider: HTMLInputElement, status: HTMLOutputElement) {
  slider.type = 'range';
  slider.min = '8';
  slider.max = '72';
  slider.step = '0.5';
  const gesture = bindHistoryGroup(editor, slider, { kind: 'range' });
  const sync = () => {
    const size = editor.snapshot().formatting?.fontSizePt;
    slider.value = String(size ?? 11);
    slider.setAttribute('aria-label', 'Font size');
    slider.setAttribute(
      'aria-valuetext',
      size === undefined ? 'Mixed or unavailable' : `${size} points`
    );
    const allowed = editor.can({
      type: 'setMarkAttr',
      mark: 'fontSize',
      attr: 'val',
      value: 22,
    });
    slider.disabled = !allowed.ok;
    slider.title = allowed.ok ? '' : allowed.reason;
  };
  const apply = () => {
    const result = editor.exec(
      {
        type: 'setMarkAttr',
        mark: 'fontSize',
        attr: 'val',
        value: Number(slider.value) * 2,
      },
      gesture.options()
    );
    status.value = result.ok ? '' : result.reason;
  };
  slider.addEventListener('input', apply);
  const off = editor.on('selectionChange', sync);
  sync();
  return () => {
    slider.removeEventListener('input', apply);
    off();
    gesture.dispose();
  };
}
```

The binding starts a range gesture on pointer down or the first relevant keydown.
It retains the handle through repeat events. Pointer release, cancellation,
lost capture, keyup, blur, or disposal ends the gesture. Outside releases work.
Terminal events end after propagation, so the final value joins the gesture.
For a held stepper, use `kind: 'repeat'` and stop your repeat timer on release.
The binding groups writes; it does not schedule repeated commands.

For native color inputs, use `kind: 'native-color'`. Remove the leading `#`
before executing a color command. Apply values in React `onChange` or Vue
`@input`; the binding owns the native `change` listener. Native `change` means
value commitment, **not popup closure**. Browser color controls differ: a
control without a terminal commitment event ends on the next activation,
Escape, blur, or disposal. Use a custom range control when exact drag boundaries
must be portable. See the [React recipe](/docs/2.x/react/hooks#usehistorygroup)
and [Vue recipe](/docs/2.x/vue/composables#usehistorygroup).

For a custom control with its own start, update, and finish callbacks, create
a handle with `editor.beginHistoryGroup()`. Keep that handle for the gesture,
pass it through `exec` options for every update, and call `end()` on finish or
cancellation. Cancellation ends grouping; it does not roll back live edits.
The following example shows one complete explicit group:

```ts
const group = editor.beginHistoryGroup();
try {
  const result = editor.exec({ type: 'setParagraphSpacing', afterPt: 12 }, { historyGroup: group });
  if (!result.ok) console.error(result.reason);
} finally {
  group.end();
}
```

Keep one handle across the asynchronous events of one gesture; end it in your
terminal handler. Creating or ending a handle does not change document content.
`end()` is idempotent and never rolls edits back. Handles belong to one editor
and mounted document. Ended, foreign, forged, and expired handles receive
`unsupported` from both `can` and `exec`. Load, detach, and destruction expire
handles. A remount also expires them; bindings create a fresh handle when needed.

Grouping supports `toggleMark`, `setMarkAttr`, `setAlignment`,
`clearFormatting`, `setLineSpacing`, `setParagraphSpacing`,
`setParagraphStyle`, and `setParagraphFormat`. Other command families refuse
`historyGroup` before mutation. This includes text and structural edits,
images, hyperlinks, notes, header/footer lifecycle, review, protection, form
fields, and content controls. Those commands can create separate package units
or deferred writes. Omit the option to run their normal history behavior.

| Event                                                                 | History behavior                                                                |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| First committed frame                                                 | `history.kind: 'started'`                                                       |
| Further frame on the same open undo entry                             | `extended`                                                                      |
| Intervening write, another group, typing flush, or local story change | Next committed frame reports `split`                                            |
| Undo or redo                                                          | Next frame starts a separate entry; facade undo/redo reports reason `undo-redo` |
| Read-only command without a group, such as `selectAll`                | Does not close the group                                                        |
| No committed history, including formatting at a collapsed caret       | `none`; no undo entry                                                           |
| Refusal before the store                                              | No history change                                                               |
| Ungrouped store transaction, even if empty or refused                 | Closes the local group                                                          |
| Ended handle                                                          | Further calls refuse; existing edits remain                                     |

The outcome comes from the history authority, not the number of accepted calls.
A repeated equal property value can still report `changed: true` and `extended`.
`changed: false` does not mean refusal: formatting at a caret can arm future typing.

Subscribe to `historyDiagnostic` for optional development feedback. A `split`
notification explains an interrupted gesture. `possible-ungrouped-gesture`
flags three ungrouped mark writes to the same selection within successive
250 ms intervals. It is a heuristic: separate clicks can be intentional.
`possible-fragmented-gesture` similarly flags creating a fresh handle for every
frame. Events do not log automatically or change grouping behavior.

`runToolbarCommand(editor, 'text.bold', { historyGroup })` accepts options in
the third position. Value slots take a typed value first:
`runToolbarCommand(editor, 'text.color', '0070C0', { historyGroup })`.
Invalid supplied values refuse instead of falling back to a fixed command.

#### Collaboration boundaries

The shared undo manager groups this session's **local origin**. A handle does
not give every collaborator the same undo stack. Grouped frames can extend
one shared item beyond the normal capture timeout. Ungrouped edits retain
collaboration's timed capture behavior; they are not always separate steps.
A story change can remain in one shared item, unlike local store history.

Another local item on top, undo/redo, or a refused journal resets shared
capture. The next committed frame reports a split. A transaction that changes
no tracked shared state creates no shared undo item. Commands that publish
separate relationship journals, including external hyperlink insertion, refuse
the grouping option.

Custom collaboration ports must preserve journal identity and synchronous local
capture. `historyGroupOfJournal(journal)` reads local metadata outside the
replicated document. Spreading, `structuredClone`, serialization, and
`postMessage` lose it. Worker ports need an explicit local identity mapping;
a serialized journal alone cannot preserve grouping or synchronous outcomes.

## The pipeline

The pipeline has one direction:

```text
bytes → bounded OPC/XML read → canonical document tree → layout → painted pages → serialize
```

The painted pages are the editable surface. There is no shadow document model to keep in sync with what you see.

Fidelity is structural. The canonical tree preserves XML content and package payloads pass through untouched. Content the engine cannot type (an unknown element, or a known one in an invalid position) becomes a generic node rather than being dropped, so unknown content never blocks editing and never disappears on save.

## Untrusted input

A `.docx` is a zip of XML that whoever sent it fully controls. The engine sanitizes at the parse boundary (URL allowlisting, entity and zip-bomb limits, recursion and element caps, no zero-click external fetches, escaping on the way back out) so everything downstream receives an already-sanitized projection.

Anything you then render from document data (a font name, a hyperlink target, a comment body, a custom node's attributes) is still attacker-controlled at your boundary. Render it as text; do not build markup or URLs from it.
