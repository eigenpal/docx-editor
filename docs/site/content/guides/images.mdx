The editor displays inline and floating DrawingML pictures (`w:drawing` with `pic:pic`). React and Vue provide controls to insert pictures, change wrapping, resize pictures, and edit alternative text. Saving preserves the picture markup and media.

The editor releases image elements and object URLs when their pages leave the painted viewport. Pages kept visible for the selection retain their images. Returning to a page recreates its images from the original package resources. Saving preserves the original media.

Pass an `ImageDecodePort` through `imageDecodePort` on `DocxEditor` to use a custom image decoder in React or Vue. You can also set this option on each adapter's root component.

## Supported formats

| Format | Insert | Layout & paint | Round-trip |
| --- | --- | --- | --- |
| PNG, JPEG, GIF | Yes, `normalizeImageBytes` preflight | Full decode at authored `wp:extent` | Original media preserved unless replaced |
| BMP, WebP | No insert | Full decode at authored `wp:extent` | Original media preserved |
| SVG | No insert | Painted at authored `wp:extent` | Original media preserved |
| TIFF, EMF, WMF | No insert | Rasterized when conversion succeeds; labeled placeholder otherwise. EMF and WMF in PDF export need the drawing module. | Preserved; no zero-click fetch |
| External `r:link` / `TargetMode="External"` | No auto-load | Placeholder + preserved rel | Preserved; explicit user gesture to embed |

Insert accepts PNG/JPEG/GIF only. Other payloads stay in the package and affect pagination through their authored extent.

The editor refuses picture insertion while another picture is selected. Place the caret in text before inserting another picture. The toolbar explains this restriction when it disables picture insertion.

The editor identifies PNG, JPEG, GIF, BMP, and WebP images from their bytes. These images can render even when the document declares another format from this list. For example, JPEG bytes declared as PNG still display. Image validation and size limits still apply. Saving preserves the original bytes and content-type declaration.

This recovery does not cover declarations that confuse these formats with SVG, TIFF, EMF, or WMF. Those mismatches show a placeholder.

JPEG validation accepts large EXIF and ICC metadata segments before the frame header. Intrinsic dimensions account for EXIF orientation, matching the browser's decoded image. The original photo bytes and the authored drawing extent remain unchanged.

BMP and WebP decode in the browser and paint like PNG or JPEG. BMP support includes top-down bitmaps and the 12-byte `BITMAPCOREHEADER`. WebP support includes lossy, lossless, and extended containers.

TIFF, EMF, and WMF paint when conversion to a validated raster succeeds. The editor and PDF export convert TIFF without extra setup. The editor rasterizes EMF and WMF without extra setup. PDF export of EMF and WMF requires the drawing module from `@docx-editor.dev/pro/drawing`, which `@docx-editor.dev/docx-to-pdf` includes. For more information, see [Advanced drawing rendering](/docs/2.x/pro/drawing). The original media stays unchanged in the package through save. When conversion is unavailable, declined, or fails, the image keeps its extent and shows a labeled placeholder.

SVG is painted through an `<img>`, which puts the browser in secure static mode: scripts in the file never run and external references in it are never fetched. Its intrinsic size is read from `width`/`height`/`viewBox` for reset-to-natural-size; layout always uses the authored `wp:extent`. An SVG whose root element cannot be read renders as a placeholder rather than inferring missing dimensions.

An inline picture in the main document text, a header, or a footer that is wider than the text area extends into the left and right page margins. The paper edge crops it. In a multi-column section, a picture extends only to the middle of the gap to a neighboring column. A picture in a table cell extends over the left and right cell margins, and the cell edge crops it. This also applies to a nested table cell. Pictures in framed paragraphs, footnotes, endnotes, and text boxes stay cropped to their text area. Layout keeps the authored size and the original image.

Inline pictures rotated by 90 or 270 degrees reserve their rotated width and height before effect margins. Text wrapping, pagination, and caret positions use these dimensions. Saving preserves the authored extent and rotation.

Header drawings positioned relative to the top margin use the physical sheet top as their origin. For these drawings outside table cells, top-and-bottom wrapping clears header text from the same origin.

`SelectedImageState.wrap` reports one of these Word menu targets:

| Value          | Text behavior                                   | OOXML mapping                |
| -------------- | ----------------------------------------------- | ---------------------------- |
| `inline`       | Places the picture in the text line             | `wp:inline`                  |
| `square`       | Wraps on both sides of a square boundary        | `wrapSquare`, `bothSides`    |
| `squareLeft`   | Wraps on the left                               | `wrapSquare`, `left`         |
| `squareRight`  | Wraps on the right                              | `wrapSquare`, `right`        |
| `tight`        | Wraps around the authored polygon               | `wrapTight`                  |
| `through`      | Wraps through the authored polygon              | `wrapThrough`                |
| `topAndBottom` | Keeps text above and below                      | `wrapTopAndBottom`           |
| `behind`       | Places the picture behind document content      | `wrapNone`, `@behindDoc="1"` |
| `inFront`      | Places the picture in front of document content | `wrapNone`, `@behindDoc="0"` |

The wrap element controls text flow. The `@behindDoc` attribute controls paint order. A picture with `@behindDoc="1"` paints behind text. If its wrap element differs from `wrapNone`, text still wraps around it. `SelectedImageState.wrap` reports that wrap mode.

Check `canResize` and `canMove` before you offer a resize or a move. They are false for a locked or hidden drawing, a rotated legacy VML text box, and in viewing mode. `canMove` is also false for an inline drawing, which flows with its line. An inline text box still resizes. `canChangeWrap` and `canCrop` apply to pictures only.

Images in front of or behind text can paint beyond their anchor cells. Their cell-relative position is preserved, but the cell does not crop these overlays. Page-relative images are clipped to the physical sheet, including its margins.

The `resourceStatus` field reports image availability:

| Status         | Meaning                                                                     |
| -------------- | --------------------------------------------------------------------------- |
| `pending`      | Validation or decoding is in progress                                       |
| `ready`        | Validated image bytes are ready to paint                                    |
| `unrenderable` | Validation, decoding, conversion, or format support failed                  |
| `external`     | The relationship points outside the package and is not loaded automatically |
| `missing`      | The relationship target is missing                                          |

## Authoring surface

Both adapters export the same parts under the same names. Default toolbar slots (contextual `image` group when a picture is selected):

| Slot | Component / hook | Engine command |
| --- | --- | --- |
| `image.insert` | `ImageInsertProvider`, `ImageInsertTrigger` | `executeImageCommand({ type: 'insertImage', … })` |
| `image.wrap` | `ImageWrap`, `useEditorValueCommand('image.wrap')` | `setImageWrapType` via `runToolbarCommand` |
| `image.altText` | `ImageAltText` | `setImageAltText` |
| `image.properties` | `ImagePropertiesTrigger`, `DocxEditorImagePropertiesDialog` | `setImageProperties` |

The packaged Insert menu carries an **Image** row that opens the same file picker as `ImageInsertTrigger`. Hide it or place it elsewhere through `DocxEditor.Menu.ImageInsert`.

`widthPoints` and `heightPoints` are the extent to insert at most. An image that fits where the caret flows keeps its natural size; a wider or taller one scales down proportionally to its cell, column, or page content box. Read the committed extent back from `snapshot().image`.

Floating pictures: select in the canvas, drag to move (`setImagePosition`), eight handles or Alt+Arrow to resize (`setImageProperties`), wrap menu for all nine choices. One undo step per completed gesture. While a picture is selected, Ctrl+Z (Cmd+Z on macOS) undoes the gesture, and Ctrl+Y or Ctrl+Shift+Z (Cmd+Shift+Z on macOS) redoes it.

Inline pictures use the same wrap menu. If you choose a floating wrap for an inline picture, the picture stays where it is on the page. Its position is measured from the left margin and from the top of its paragraph, so it moves with the text. In a table cell, header, footer, or paragraph frame, the picture starts at the top-left corner of its column and paragraph. A picture with a move lock keeps its wrap.

## Wrap modes and text reflow

Wrap changes are **layout-structural**: exclusion zones feed line breaking before paint. Square/tight/through use authored polygons (with distances and `effectExtent`); top-and-bottom and square variants reflow body text accordingly. Header/footer rule: page-relative anchored letterheads do **not** inflate the header box. Body flow height still sizes the furniture band.

Text distances inherit each missing side from `wp:anchor`; an explicit wrap-child value, including zero, overrides that side. When square or rectangular tight wrapping leaves no passage wide enough for the next glyph, text clears the image before continuing. The clearance participates in pagination without repeating the gap on subsequent lines. Nonrectangular contours keep their existing scanline behavior.

When a floating picture splits a line into passages, each part of the line aligns inside its own passage. Centered text is centered on each side of the picture, right-aligned text ends at the right edge of each passage, and justified text fills each passage. This applies in the body, table cells, headers, footers, and text boxes. Right-to-left paragraphs align the line as a whole. A square wrap with `wrapText="largest"` keeps text on the wider side of the picture only.

A line break (`w:br`) with `w:clear` restarts the text after it on the next line that the floating objects on one side do not interrupt. The picture keeps its position; only the restart line moves.

- `left` clears the objects that block the start of the line that holds the break.
- `right` clears the objects that come after the break on that line.
- `all` clears every object that wraps text, including objects from earlier paragraphs and objects in the same table cell.

Objects with no text wrapping, in front of text or behind it, are not cleared. If the restart line does not fit above the bottom margin, it starts on the next page or column. The value `none` lays out as an ordinary line break, and the attribute is kept when you save.

A positioned table keeps its text wrap region when nearby pictures require immediate placement. Body text clears that region.

An inline picture flows like a word. If it does not fit before a floating picture, it continues past the floating picture on the same line. Text after an inline picture starts at the picture's edge, and a click past the picture places the caret after it. A click in the space that a floating picture leaves between two pieces of content places the caret between them.

## Accessibility

Alt text uses `@descr`, then `@title`; `@name` is never announced. A picture with neither description nor title is exposed as decorative. Hidden drawings (`@hidden`) suppress paint, hit-testing, and handles while remaining preserved on save.

## Security and external images

- No network fetch on open, layout, paint, or save for external relationships.
- Embedded bytes are signature-checked and dimension-capped before decode.
- Hyperlinks on drawings (`a:hlinkClick`) require an explicit gesture and pass through `sanitizeHref`.
- Optional explicit download-and-embed path for external targets is user-initiated only (bounded size/content-type).

## Custom unsupported-content components

Register a component for unsupported inline or block content, or for the built-in placeholder of a drawing or equation. Match the original OOXML namespace and element name without a fixed list of element kinds. Custom rendering preserves the canonical source and saved DOCX content.

<FrameworkTabs>
<Framework value="react">

```tsx
<DocxEditor document={bytes}>
  <DocxEditor.UnsupportedElement
    match={(element) => element.namespaceUri === 'urn:my-widgets'}
    layout={{ width: 180, height: 48 }}
  >
    {({ element }) => <MyUnsupportedContent element={element} />}
  </DocxEditor.UnsupportedElement>
</DocxEditor>
```

Return `null`, `false`, an empty fragment or array, or whitespace to keep the built-in placeholder. The check reads only the value that your function returns. A child component that renders `null` replaces the placeholder with an empty box. The same declaration works inside `DocxEditor.Root` beside `DocxEditor.Content`.

</Framework>
<Framework value="vue">

```vue
<DocxEditor :document="bytes">
  <DocxEditor.UnsupportedElement
    :match="(element) => element.namespaceUri === 'urn:my-widgets'"
    :layout="{ width: 180, height: 48 }"
  >
    <template #default="{ element }">
      <MyUnsupportedContent :element="element" />
    </template>
  </DocxEditor.UnsupportedElement>
</DocxEditor>
```

A default slot that renders nothing, such as a slot whose `v-if` is false, keeps the built-in placeholder. The same declaration works inside `DocxEditor.Root` beside `DocxEditor.Content`.

</Framework>
</FrameworkTabs>

Both packages export `UnsupportedElement` with these fields:

- `nodeId` and `ownerPartName` identify the source element and its document part.
- `namespaceUri` and `localName` identify the OOXML element.
- `source` exposes the read-only canonical source. Treat document values as untrusted data.
- `placement` is `inline` or `block`, as determined by the source position.
- `label` contains the text of the built-in placeholder.
- Optional `drawing` and `equation` records provide engine metadata. `drawing.placeholderGraphicKind` names the kind of graphic: `chart` (a chart), `diagram` (SmartArt), `textbox` (a DrawingML shape, with or without text), `group` (a shape group), `canvas` (a drawing canvas), `shape` (a legacy VML drawing, such as WordArt), or `graphic` (any other graphic). A picture placeholder, such as an EMF, WMF, or TIFF picture that does not convert, has `null`. `drawing.accessibility.label` holds the drawing's alternative text. Every chart drawing whose chart part can be read also has `drawing.chart`, with the chart's `title`, `plotTypes`, and `shownAs`, which says whether the page draws the chart (`chart`), shows its fallback (`fallback`), or shows the placeholder (`placeholder`). A declaration replaces only a placeholder, so inside a declaration `shownAs` is always `placeholder`. To tell a drawn chart from a chart shown by its fallback, read the layout records without an editor, as [Replace a placeholder](/docs/2.x/pro/drawing#replace-a-placeholder) shows.
- Optional `bounds` describes the box after layout. Use source metadata for matching before pagination.

Omit `match` for a catch-all. The first mounted matching declaration wins. Prop updates retain priority. Removing and remounting a declaration gives it a later priority. Use matchers that do not overlap, or keep declarations mounted and change their matchers to disable them temporarily. An empty result keeps the built-in placeholder; it does not try the next declaration.

`layout` reserves width and height in document points before pagination for opaque content. Defaults are 120 × 24 points for inline content and 240 × 96 points for blocks. Dimensions must be finite, positive, and at most 100,000 points. Drawing and equation placeholders retain their engine layout boxes. Unmatched opaque content retains its invisible behavior.

Components retain declaration-local framework context and local state across same-page repaints. They can unmount when an occurrence leaves its page, is virtualized, or the document or registration changes. Keep durable annotations in application state. Controls own their keyboard, clipboard, context-menu, and drop events. Fit controls within the reserved box, or use scrolling or an external panel.

Properties, metadata, and private payloads inside owning drawing, equation, and field projections are not independent content occurrences. These declarations replace placeholders only; they do not render charts, SmartArt, or other DrawingML themselves. To show a chart's title in place of its placeholder, see [Replace a placeholder](/docs/2.x/pro/drawing#replace-a-placeholder); the recipe works without the EigenPal Pro License. Standalone low-level painters without a source lookup can expose `source: null`.

## Drawing limits

The editor renders brightness, contrast, grayscale, and bilevel black-and-white picture adjustments. It preserves image alpha and adjustment markup when you save. PDF export does not apply these adjustments.

| Drawing content | Status |
| --- | --- |
| Solid shapes and bounded shape groups | Render geometry with sRGB or theme colors |
| One picture in a shape group, below the group's shapes | Render in its own frame, as described in [Pictures in shape groups](#pictures-in-shape-groups) |
| Charts | Render read-only when you register `drawingModule()` from `@docx-editor.dev/pro/drawing`. A chart that does not render shows its saved fallback picture or drawing when it has one. Its fallback produces no PDF diagnostic and can differ from the chart's cached values. Otherwise, the editor preserves the extent and shows a labeled placeholder, and PDF export leaves the chart out with a `drawing` diagnostic, which fails the default strict export. A chart in an `mc:Choice` that the reader skips, with an empty `mc:Fallback`, does not show. Copy and cut of a selection that includes a chart are refused. With change tracking on, deleting a chart records one tracked deletion of the whole chart. Treemap, sunburst, and map charts, and charts that combine a pie or radar plot with other plot types, do not render. For the list, see [What renders](/docs/2.x/pro/drawing#what-renders). |
| SmartArt | Render the saved diagram drawing read-only. A diagram saved without its drawing renders when you register `drawingModule()`. Without the module, it shows a labeled placeholder |
| Glow, inner shadow, reflection, soft edge, and dark-edged bevel rim | Render when you register `drawingModule()`. Without the module, the shape or picture paints without these effects |
| Drawing canvases | Render shapes, connectors, and text read-only |
| Unsupported groups and drawings | Preserve the extent and show a labeled placeholder. In alternative content (`mc:AlternateContent`), a drawing that cannot render uses the fallback content. If neither renders, it is not shown, except charts, which show a placeholder. A chart in an `mc:Choice` that the reader skips, with an empty `mc:Fallback`, is not shown either. A floating drawing with a wrapping mode still reserves its wrap area |
| Anchored text boxes | Render clipped stories, edit supported body text boxes, and drag or resize their borders |
| Page fields in anchored header or footer text boxes | Evaluate per page |
| Inline text boxes | Render clipped stories on the line and edit supported body text boxes. They move with their line, so they cannot be dragged or resized |
| Text boxes inside text boxes, linked chains, autofit, and rotation | Show a placeholder or clip |
| Standalone VML (`w:pict`) | Render the subset described in [Legacy VML previews](#legacy-vml-previews) |
| `w:object` and `w:altChunk` | Preserve as generic content with diagnostics |
| Tracked image insertion and deletion | Record the change in suggesting mode |
| Tracked image property edits | Stay unavailable in suggesting mode |
| Picture artistic effects (`a14:imgEffect`) | Do not render; authored markup round-trips. Glow, inner shadow, reflection, and soft edge in `a:effectLst` render with the drawing module. |

## Pictures in shape groups

A DrawingML shape group (`wpg:wgp`) can hold one picture member beside its shape members. For example, a scanned letterhead page can sit behind the text with ruled lines drawn over it. The editor and PDF export render the picture in its own frame inside the group, then render the group's shapes over it.

The picture renders only if all of these conditions are true:

- The group holds exactly one picture, and the picture comes before every shape member.
- The picture is not rotated or flipped, it has a rectangle geometry, and its fill is not tiled.
- The picture is visible and has no image effects, visible outline, shape effects, or 3D properties.
- Its fill rectangle has no offsets. An omitted fill rectangle uses the full picture frame.
- The picture frame overlaps the group's area and extends no more than one group width or height past it.
- Every other member of the group is a supported solid shape.

If a condition is false, the group is an unsupported group. Word stores most groups in alternative content (`mc:AlternateContent`). An unsupported group in alternative content is not shown. Other unsupported groups show a labeled placeholder. Text boxes inside a group do not render, so a group with a text box member is an unsupported group.

An unsupported group in alternative content still takes part in layout if it floats with square, tight, through, or top-and-bottom wrapping. Text flows around its wrap area as it would around the group if it were shown. The hidden group paints nothing and cannot be selected, and exports do not include it. A group with no wrapping (`wp:wrapNone`) takes no space.

A group renders completely or not at all. While the picture loads, the editor renders the group's shapes alone. If the picture cannot load, the editor and PDF export treat the group as an unsupported group. For example, the picture is missing, linked, damaged, or over a decode limit. PDF export embeds PNG and JPEG pictures only. If a group in alternative content holds a picture in another format, PDF export leaves the group out and reports an `information` diagnostic. PDF export reports other groups that it cannot render as `unsupported`.

The picture is clipped to the group's area. The group's shapes can extend into the effect extent (`wp:effectExtent`), as the shapes of a group without a picture can.

Picture commands, such as resize and replace, do not apply to a picture in a group. Markdown export omits the group as one drawing and reports an `omitted-drawing` warning. Saving preserves the group, its alternative content, and its media without changes. An embedded picture passes the normal image validation and decode limits. A linked picture is never fetched.

## Insert and edit text boxes

Choose **Insert → Text Box** from a body paragraph to add an empty rectangular box and start typing. The new box has a white fill, a black border, and a fixed starting size. Drag its border to move it, or drag its handles to resize it. Clicking its text shows the frame and places the caret. Insertion in tables, headers, and footers is unavailable.

## Edit text boxes

Click inside an unrotated text box in the body to edit its paragraphs. A frame outlines the box being edited. Drag the frame's border to move an anchored box, or drag its handles to resize the box. An inline text box resizes but moves only with its line.

To edit a text box in a header or footer, follow these steps:

1. Double-click the box. Its header or footer opens with the caret in the box.
2. Type, format, or paste. Pasting into a text box inserts plain text.
3. Press **Escape** to leave the box. The box stays selected, so you can press **Delete** to delete it, drag it, or press **Enter** to go back into its text.
4. Press **Escape** again to close the header or footer.

While a header or footer is open, a single click enters any of its boxes. **Undo** reverses each step, and the edits synchronize during collaboration.

These text boxes keep their geometry or their text as authored:

- A box whose text is rotated or vertical, or a box that holds a table, takes no caret. Clicking it selects the box instead, and its frame says why the text cannot be edited.
- A rotated legacy VML text box, and one sized as a percentage of the page or margin, cannot be moved or resized. Its frame has no handles.
- To edit a box that sits behind the text of a header or footer, open the header or footer first, and then click the box.
- Table insertion is unavailable inside a text box.

Legacy VML text boxes take the same controls as modern ones. Moving or resizing one rewrites only its position and size.

## Find text in text boxes

**Find** searches anchored and inline text boxes in the body, headers, and footers. Selecting a match selects its text box. Text boxes in footnotes or endnotes are not searched.

Use `useDocumentSearch` to add Find navigation to a custom [React](/docs/2.x/react/hooks#usedocumentsearch) or [Vue](/docs/2.x/vue/composables#usedocumentsearch) interface.

## Legacy VML previews

Standalone `w:pict` can render unrotated embedded photos and bounded groups of photos, solid rectangles, rounded rectangles, and ellipses, straight line segments with arrows, and, with the drawing module, WordArt on a text path (`_x0000_t136` to `_x0000_t175`). A floating `v:line` spans its `from` and `to` points and also renders in PDF export. Group-local coordinates, picture crops, supported text wrapping, aligned positions, and source order are retained. A shape without `position:absolute` in its style is inline. Without the drawing module, inline WordArt keeps its extent with a placeholder, and floating WordArt does not render. WordArt uses the authored font when available on the host. Curved WordArt renders when the drawing includes its shape definition, or for the arch shape.

Floating `v:shape` paths with two explicit points can have one zero extent. They paint as native vector lines. A zero coordinate axis requires both corresponding coordinates to match its origin. Curves, multiple subpaths, and invalid coordinate axes remain opaque.

A text box (`v:textbox`) on a rectangle, rounded rectangle, or text box shape lays out its story inside the shape with the `inset` margins, floating or inline, in the body, headers, and footers. It paints the solid fill and outline of the shape. **Find** reaches its text, and a box in the body, a header, or a footer takes the same editing as other text boxes. For more information, see [Edit text boxes](#edit-text-boxes).

Other previews are read-only. Saving preserves the original VML, media, and relationships without adding generated SVG parts or converting the source to DrawingML. Deleting another picture preserves shared photo relationships.

The editor does not partially render unsupported, oversized, or clipped groups. Custom templates, text boxes, curves, image effects, rotation, and unsupported group members prevent a group preview. Only recognized standard shape templates are supported. When a document supplies DrawingML and VML alternatives, the editor displays only the selected alternative.

An inline standalone photo can have a picture border (`w10:border*`) when all four sides use one `single` line with the same width and color. The photo keeps its authored size and crop, and the border line surrounds it. The drawing grows by the line width on each side. Other border combinations, and borders on floating, color-keyed, or grouped photos, prevent the preview.

An inline embedded object (`w:object`) shows its cached preview picture when the preview is one standard picture shape (`_x0000_t75`) with an embedded image. The object takes one position in the text, and layout reserves the preview size. The editor never runs, loads, or resolves the embedded object, and never fetches a linked preview. Picture commands, such as resize and replace, do not apply to the preview. You can delete the object with the text around it; the embedded binary stays in the package. Copy and cut refuse selections that contain an object. Rich paste refuses fragments that contain an object and preserves the target selection. A WMF or EMF preview keeps its size and shows a labeled placeholder when conversion is unavailable. Objects inside paragraph frames show no preview or reserved preview size. Direct frames and frames inherited from paragraph styles have this limit. The object keeps its text position, and the surrounding text stays unchanged. Floating objects, linked objects, and objects with other content show no preview.

Standalone photos reuse validated image resources and retain their authored crop. Groups, WordArt, and color-key previews use bounded static SVG resources. Embedded members still pass the normal image validation and decode limits; an external or missing member never triggers a fetch or a misleading partial group preview.
