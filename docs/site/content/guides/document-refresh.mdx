Use `createDocumentRefresh(editor)` to display complete DOCX files that your server returns. The controller keeps the editor instance, subscriptions, and scroll position. It can reload the document, or apply the result as one undoable edit. Your application receives each result; the editor does not watch files or URLs.

The controller is a host integration API, separate from the Office.js-shaped automation model. If your agent can issue document edits, use [Revisions](/docs/2.x/editor-api/revisions) instead.

## API overview

Call `createDocumentRefresh(editor)` after the editor mounts. Repeated calls for one editor return the same controller. Import it from your adapter or `@docx-editor.dev/core/editor`.

| Method | Purpose |
| --- | --- |
| `capture()` | Capture the current bytes and revision. Returns a submission. |
| `applyUpdate(update)` | Accept a complete DOCX for that submission and sequence. Set `mode: 'edit'` to apply it as one undoable edit. Returns a success or refusal result. |
| `finish(submission)` | Close the submission when the job ends. Accepted content and change navigation stay. |
| `cancel()` | Invalidate pending results. It does not cancel your network request. |
| `highlightChanges(options?)` | Highlight available changes. Returns the selected available change count, including offscreen locations, or `0` during replacement. |
| `clearHighlights(options?)` | Dismiss highlights, with or without a fade. |
| `navigateToChange(id, options?)` | Reveal a change location. Returns whether it is available. |
| `snapshot()`, `subscribe(listener)`, `onResult(listener)` | Read cached status, observe changes, and receive every result, including refusals. Both listeners return an unsubscribe function. |
| `recover()`, `recoveryBytes()` | Retry restoration after a failed replacement, or get the previous bytes. |

The flow is `capture()`, then your server job, then `applyUpdate()`, then `finish()`.

## Apply an updated DOCX

<a id="accept-an-updated-file" />

Capture the document, send its bytes to your backend, and apply the response:

```ts
import { createDocumentRefresh } from '@docx-editor.dev/react';

const refresh = createDocumentRefresh(editor);
const submission = await refresh.capture();

try {
  const response = await fetch('/api/update-document', {
    method: 'POST',
    body: submission.bytes,
  });
  if (!response.ok) throw new Error('Processing failed');

  const result = await refresh.applyUpdate({
    submission,
    sequence: 1,
    bytes: await response.arrayBuffer(),
  });
  if (result.ok) {
    refresh.highlightChanges();
  } else {
    showRefreshError(result.code);
  }
} finally {
  refresh.finish(submission);
}
```

Get `editor` from `useDocxEditor()` inside the editor root. React returns an instance or `null`; Vue returns a shallow ref.

- `capture()` commits buffered input and form input, and waits for text composition to end.
- Pass the same `submission` object to `applyUpdate()`. A copied, superseded, or other editor's token cannot authorize replacement.
- Any edit after capture makes `applyUpdate()` return `local-edits`, even after undo. Capture again; do not replay the old result.
- `applyUpdate()` resolves after the replacement lays out its opening pages and accepts clicks.

## Apply an update as one undoable edit

<a id="undoable-update" />

By default, `applyUpdate()` reloads the document, which resets selection and undo history. To keep both, pass `mode: 'edit'`. The editor applies the difference between the open document and the returned file as one edit, through the [`replaceDocument` command](/docs/2.x/guides/loading-and-saving#replace-the-document-as-one-undoable-edit):

```ts
const submission = await refresh.capture();
const bytes = await processDocument(submission.bytes);

let result = await refresh.applyUpdate({ submission, sequence: 1, bytes, mode: 'edit' });
if (!result.ok && result.code === 'edit-unsupported') {
  // The document and its undo history are unchanged. Outside a
  // collaboration session, reload instead.
  result = await refresh.applyUpdate({ submission, sequence: 1, bytes });
}
```

An update with `mode: 'edit'` behaves as follows:

- One undo returns the document to the captured submission, and one redo applies the result again. Undo steps from before the update stay available.
- The content matches what a reload of the returned file shows. Pending tracked changes keep their authors and dates, and comments keep their IDs and threads. The update creates no revisions of its own, even in suggesting mode.
- The caret and selection stay in their paragraphs when those paragraphs survive. If the update removes a paragraph, its caret moves to the end of the nearest earlier paragraph. The scroll position stays where it is.
- Each accepted cumulative result adds one undo step, so undo after the second result returns to the first.
- The `change` event has `source: 'refresh'`, so it does not start another processing job. Undo and redo are user edits and omit `source`.
- A result identical to the open document succeeds without an undo step.

If the difference cannot apply as an edit, for example because the returned file names a different main document part, the update refuses with `edit-unsupported`. Nothing changes, and you can retry the same sequence with a reload. In a collaboration session, a reload refuses with `collaboration`, so report the failure instead.

An editor in viewing mode refuses the update with `edit-not-permitted`. So does a document whose enforced protection permits only comments, form fields, tracked changes, or no edits, because the update is an untracked edit. Protection refuses the whole update, even when the document has editable ranges. Outside a collaboration session, a reload of a protected document still works.

### Refusal causes

A refused update has a stable `code` and an English `message` for logs. With `mode: 'edit'`, it can also carry `reason`, a `RefreshRefusalReason` that names the specific cause. Each `reason` belongs to one `code`, so checking `reason` also narrows `code` in TypeScript:

| `reason` | `code` | Situation |
| --- | --- | --- |
| `viewing` | `edit-not-permitted` | The editor is in viewing mode. |
| `protected` | `edit-not-permitted` | Enforced document protection does not permit an untracked edit. |
| `collaboration-unavailable` | `unavailable` | The collaboration session cannot accept edits now. |
| `different-main-part` | `edit-unsupported` | The returned file names a different main document part. |
| `unsupported-difference` | `edit-unsupported` | The difference cannot be expressed as an edit of the open document. |
| `collaboration-refused` | `edit-unsupported` | The collaboration room refused the edit, for example because a value exceeds its size limits. |

```ts
if (!result.ok && result.reason === 'collaboration-refused') {
  // Reprocessing returns the same file, so report it instead of retrying.
  // reportProcessorFailure is your own error reporting.
  reportProcessorFailure(result.message);
}
```

### Collaboration sessions

An update with `mode: 'edit'` works while a collaboration session is attached. Other participants receive the update as an ordinary edit, and it converges with their concurrent edits:

- Undo on the participant who applied the update takes back that update only. Edits that other participants made meanwhile stay.
- An edit by any participant after `capture()` refuses the update with `local-edits`. Capture again and process the newer document.
- An update made while offline reaches other participants when the connection returns, if your session enables offline editing.
- If the session cannot accept edits now, the update refuses with `unavailable`. If the room refuses the update, for example because a value exceeds its size limits, the update refuses with `edit-unsupported`. The document keeps the room's content, and `change` listeners still see the edit and its reversal.

A reload still refuses collaboration sessions with `collaboration`, because it would replace the shared document for every participant.

## Receive cumulative results

The processor assigns each result a nonnegative integer `sequence`. Each file holds the complete cumulative output for the submission:

```ts
const submission = await refresh.capture();

try {
  for await (const update of receiveProcessorUpdates(submission.bytes)) {
    const result = await refresh.applyUpdate({
      submission,
      sequence: update.sequence,
      bytes: update.bytes,
      changes: update.changes,
      failures: update.failedOperationIds,
    });
    if (!result.ok) {
      if (result.code === 'out-of-order') continue;
      showRefreshError(result.code);
      break;
    }
    showChanges(result.changes);
    showPartialFailures(result.failures);
  }
} finally {
  refresh.finish(submission);
}
```

| `update` field | Meaning |
| --- | --- |
| `submission` | The object that `capture()` returned. |
| `sequence` | Processor order, never network arrival order. Duplicate or older sequences return `out-of-order`. Replacements run one at a time, and only a successful load advances the accepted sequence and revision baseline. |
| `bytes` | The complete DOCX, as `ArrayBuffer` or `Uint8Array`. |
| `mode` | `'reload'` (default) or `'edit'`. See [Apply an update as one undoable edit](#undoable-update). |
| `changes` | Optional change metadata. See [Provide change locations](#provide-reliable-change-locations). |
| `failures` | Optional failed processor operation IDs. The controller reports them and never retries them. |

Do not start processing from every `change` event. Replacements and undoable updates have `source: 'refresh'` or `source: 'recovery'`, loads have `source: 'load'`, and user edits omit `source`:

```ts
editor.on('change', (change) => {
  if (change.source) return;
  scheduleProcessing();
});
```

## Provide change locations

<a id="provide-reliable-change-locations" />

A plain file does not identify its changes, and the controller does not compare files. Without metadata or tracked revisions, the result reports `changeInformation: 'unavailable'`. Supply metadata with stable IDs across cumulative results:

```ts
const result = await refresh.applyUpdate({
  submission,
  sequence: 2,
  bytes: updatedBytes,
  changes: [
    {
      id: 'delivery-date',
      description: 'Changed the delivery date',
      location: { paragraphId: '00A12B34', start: 10, end: 20, text: 'October 12' },
    },
    { id: 'removed-clause', description: 'Removed a clause', unavailableReason: 'deleted' },
    { id: 'footer-version', description: 'Updated the footer version' },
  ],
});
```

| Location rule | Detail |
| --- | --- |
| Selector | Exactly one of `paragraphId` (the `w14:paraId`) or `paragraphIndex` (zero-based body order, including table paragraphs). |
| Paragraph ID | Eight hex digits from `00000001` through `7FFFFFFF`, case-insensitive. Loading normalizes invalid or duplicate IDs, so use IDs from the returned file. |
| Offsets | UTF-16 code units, a nonempty range within one body paragraph. |
| `text` | Must equal the returned text between `start` and `end`. |
| `description` | Up to 1000 characters, returned unchanged. Render it as text. |

Invalid location metadata does not reject valid document bytes. That change gets a non-`available` status and a `diagnostic.code`, with the requested `diagnostic.location`:

| Diagnostic code          | Meaning                                                    |
| ------------------------ | ---------------------------------------------------------- |
| `invalid-selector`       | Both selectors, neither, or an invalid paragraph index.    |
| `invalid-paragraph-id`   | The ID is outside the supported hex range.                 |
| `paragraph-not-found`    | The returned document lacks the paragraph.                 |
| `ambiguous-paragraph-id` | Several paragraphs match the ID.                           |
| `invalid-offsets`        | The offsets do not form a nonempty range in the paragraph. |
| `text-mismatch`          | The returned text differs from `text`.                     |
| `not-rendered`           | The paragraph has no layout position.                      |
| `missing-location`       | The change has no location.                                |
| `deleted`                | The deleted content has no surviving location.             |
| `unsupported-story`      | A revision is outside the body.                            |
| `multiple-paragraphs`    | A revision spans several paragraphs.                       |

If you omit `changes`, a registered review module supplies tracked revision locations. Revisions present at capture do not count as new. The review module requires the EigenPal Pro License.

## Present changes

Highlight new available changes after a successful `applyUpdate()`, then navigate:

```ts
const target = refresh
  .snapshot()
  .changes.find((change) => change.isNew && change.status === 'available');

if (target && refresh.navigateToChange(target.id, { block: 'centerIfNeeded' })) {
  refresh.highlightChanges({ changeIds: [target.id], timeoutMs: 3000 });
}
```

- `isNew` marks new IDs, changed text, and changed descriptions within one submission.
- Locations stay valid until the next accepted result or local edit.
- Highlights change presentation only. They add no saved bytes and no undo entries.
- Keep a text change list beside the document, because color alone does not explain a change.

### Customize highlights and motion

`RefreshHighlightOptions` extends `AnchorHighlightOptions`. The shared color, border, padding, timing, and animation options are listed in [Highlight a paragraph reference](/docs/2.x/guides/navigation#highlight-a-paragraph-reference). Refresh differs in these options:

| Option | Default | Meaning |
| --- | --- | --- |
| `changeIds` | Omitted | Select these IDs, including earlier changes. Overrides `includePrevious`. An empty array dismisses highlights. At most 10000 nonempty string IDs. |
| `includePrevious` | `false` | Also highlight earlier changes in the latest cumulative result, not only new ones. |
| `color` | `var(--doc-refresh-highlight-color)` | The refresh theme token, separate from the anchor token. |

Each call starts from the defaults, so reuse one options object. Repeated calls reset the timeout without replaying the entrance. To replay it, call `clearHighlights({ animation: false })` first.

- `highlightChanges()` validates options even when change locations are stale or unavailable.
- `animation.exitDurationMs` defaults to `durationMs` and accepts `0` through `10000` milliseconds.
- Expiration removes the styling. Change metadata and navigation stay available.
- Without overrides, `clearHighlights()` uses the last requested exit duration and easing. `snapshot().highlightsVisible` becomes `false` when dismissal starts, before the exit animation ends.

### Control change navigation

`navigateToChange()` takes `NavigateToChangeOptions`:

| Option | Default | Meaning |
| --- | --- | --- |
| `block` | `'center'` | `'start'`, `'center'`, `'centerIfNeeded'`, or `'nearest'`. |
| `behavior` | `'instant'` | `'smooth'` for an explicit animated action. |
| `offsetPx` | `24` | Nonnegative edge padding for `'start'` and `'nearest'`, in CSS pixels. |
| `focus` | `false` | Move focus and the caret to the change start. |

Navigation returns `false` for an unavailable location or during replacement. It does not wait for smooth scrolling. Invalid modes throw `TypeError`; invalid padding throws `RangeError`.

## Handle refusals and recovery

`applyUpdate()` returns `{ ok: false, code, message }` with a `RefreshFailureCode`. `message` is an English explanation for logs; do not parse it. Edit refusals also carry a `reason`; see [Refusal causes](#refusal-causes). `capture()` rejects with `DocumentRefreshError`, whose `code` is a `RefreshFailureCode`. Handle codes, not messages:

| Code | Situation | Action |
| --- | --- | --- |
| `local-edits` | The document changed after capture, even through undo. With `mode: 'edit'`, this includes another participant's edit. | Capture again and start a new job. |
| `out-of-order` | A duplicate or older sequence arrived. | Discard the result. |
| `superseded` | The result belongs to an inactive submission, or arrived after cancellation. | Discard it. |
| `document-changed` | The document changed during replacement. | Discard it. |
| `cancelled` | Cancellation interrupted a replacement. | Stop the transport. |
| `collaboration` | A reload while a collaboration session is attached, even if disconnected. | Use `mode: 'edit'`. |
| `unavailable` | No mounted document, the document is still opening, or the collaboration session cannot accept edits now. | Retry later. |
| `edit-not-permitted` | An update with `mode: 'edit'` in viewing mode or on a protected document. A retry does not help. | Change the editing mode, or reload outside a collaboration session. |
| `busy` | A replacement is running, or a preview blocks edits. | Wait for it to finish. |
| `edit-unsupported` | The result cannot apply as an undoable edit. The document and its history are unchanged. | Outside a collaboration session, retry the same sequence without `mode: 'edit'`. |
| `invalid-result` | The update object is malformed, such as a change with wrong field types. | Fix the update. |
| `invalid-document` | The bytes are not a valid DOCX. The visible document stays. | Report the processor failure. |
| `input-failed` | Pending input or serialization failed. | Report the failure. |
| `load-failed` | A valid file failed to mount. Check `recovered` for restoration. | Report the failure. |
| `recovery-failed` | Mounting and restoration both failed. | Offer recovery. |

Do not retry a refused result blindly. Connect your cancel control to both the transport and the controller, because cancellation does not reverse accepted files:

```ts
const transport = new AbortController();
// Pass transport.signal to your fetch calls.
function cancelProcessing() {
  transport.abort();
  refresh.cancel();
}
```

When `refresh.snapshot().recoveryAvailable` is `true`, offer two controls:

- `await refresh.recover()` reloads the previous document, resets selection and undo history, and resolves `false` on failure.
- `refresh.recoveryBytes()` returns the document from before the failed replacement, for download.

Recovery bytes are not an undo archive for accepted files.

## Limits

- A reload replaces the whole document and resets selection, undo history, and some review state. An update with `mode: 'edit'` keeps them.
- A reload refuses collaborative sessions, including disconnected ones.
- An update with `mode: 'edit'` maps the caret only within its own paragraph. A caret inside rewritten text moves to the end of that text.
- Scroll uses pixel offsets. A shorter file clamps the offset; neither case keeps the same subject in view.
- The controller does not compare document meaning or reject unrelated content. Check document and job identity in your application before `applyUpdate()`.
- An ordinary `editor.load()` invalidates pending submissions and recovery.
- Highlight numbers must be finite. `padding`, `borderRadius`, and `borderWidth` must be nonnegative. `timeoutMs` accepts `0` through `2147483647` milliseconds, or `null`.
- Reduced-motion preferences cap fades at 125 milliseconds and make smooth navigation instant.
