### Text and formatting

<FeatureMatrix category="text" />

Raised and lowered text contributes to automatic and minimum line heights. This includes inherited `w:position` values combined with subscript or superscript. Exact line spacing retains its authored height.

#### Equation source formatting

Latin and Greek letters in equations use mathematical italic glyphs from the math font, unless `m:sty` specifies plain, bold, or bold italic. Run fonts, bold, and italic do not change these letters. Plain-style runs keep the run font, and a font other than Cambria Math also keeps run bold and italic. Normal-text runs keep their original characters and run formatting. Measurement and paint use the same display string; saved OMML retains the original text.

Equations retain their canonical Office Math source when you save the document. Literal text and normal text project within fractions, radicals, scripts, and other supported structures. Upper and lower bars also project as math. Bars, fractions, radicals, scripts, and n-ary operators project when their properties carry control properties (`m:ctrlPr`). The control properties can hold run fonts, bold, and italic, directly or inside a tracked insertion or deletion. They can also hold default formatting, which this section describes later. Operator glyphs and rules keep the default math formatting, and the control properties remain unchanged on save. Other content in control properties retains the text fallback.

Control properties hold default formatting when their run properties contain only the Cambria Math font, italic, one font size, and a language. If every control property in an equation holds the same default formatting, compact equation replacement is available. The replacement writes the same control properties on each fraction, radical, script, and n-ary operator that it creates. Run properties (`w:rPr`) on equation runs follow the same rule. If every run in an equation holds the same default formatting and no math run properties (`m:rPr`), compact equation replacement is available. The replacement writes the same run properties on each run that it creates. If the runs share one font size, the equation lays out at that size. Otherwise, it takes the size of the surrounding text. A display equation takes a run size only when all of its equations share it. Compact equation replacement is disabled when it cannot preserve run formatting, bars, or other control properties, including tracked ones. You can remove the equation and edit ordinary text beside it. This restriction applies to the equation, not the document. Unsupported source properties retain the text fallback and remain unchanged on save.

### Paragraphs and styles

<FeatureMatrix category="paragraphs" />

#### Automatic inter-script spacing

Paragraphs use automatic spacing between East Asian text and Latin letters or ASCII digits by default. `w:autoSpaceDE` and `w:autoSpaceDN` control the two boundary types through the paragraph style cascade. An authored false disables the corresponding spacing. Source text and UTF-16 offsets remain unchanged. Line fitting, table widths, caret positions, and paint use the same advance across source run boundaries.

East Asian text adds one quarter of its authored font size before Latin letters or ASCII digits. The reverse boundary adds half the average character width of the authored Latin font. Aptos, Arial, Calibri, Calibri Light, Cambria, Century, Century Gothic, Courier New, and Times New Roman keep their own value when a substitute font draws them. Other fonts need their own font file, or the reverse boundary adds no gap. Explicit character spacing, scaled or shifted text, equations, projected fields, and right-to-left runs keep their existing advances. Vertical Japanese layout and all legacy Word compatibility rules remain outside this subset.

#### Tabs and paragraph keeps

In left-to-right text, an opening word wraps within the space after leading left-aligned tabs. The tabs retain their advances and do not add a blank line. This applies to ordinary text without floating objects beside it, including table cells.

A paragraph with `w:keepNext` stays with the opening lines that the following paragraph must keep together. With widow control, a following three-line paragraph stays whole. `w:keepLines` keeps the entire following paragraph together when the group fits on a page. Consecutive kept paragraphs form one group, including groups with more than eight paragraphs. Inherited keep properties apply to the complete group. Explicit page breaks and section boundaries end the group.

#### Text frames

Body text frames retain numeric and relative page, margin, or text positions. The engine supports fixed width. Frames with omitted width use the containing text column. It supports `auto`, `atLeast`, and `exact` height rules. A positive authored height sets a minimum when the height rule is absent. Exact-height frames clip content to the authored rectangle. Frame attributes inherit individually from paragraph styles. Wrapping defaults alone do not create a positioned frame. Adjacent paragraphs with identical resolved `w:framePr` attributes share one frame. Inline pictures remain inside their frame.

All `ST_Wrap` values use the frame's rectangular contour. `auto` uses the default `around` behavior. `none`, `notBeside`, and vertical `inline` alignment move following text below the frame. Single-line left-to-right dropped caps use the requested body-line band. Multiline dropped caps retain ordinary flow. Right-to-left dropped caps retain ordinary flow. Margin caps sit outside the text column on either side.

Frames follow their next ordinary paragraph across page breaks and do not consume normal paragraph height. Bounded negative page-relative and margin-relative offsets remain authored. Negative text-relative vertical offsets retain ordinary flow to prevent overlap with earlier text. Locked anchors remain attached during supported text, property, split, and join edits. A following continuous section clears preceding frames that intersect the body area. Frames outside that area do not advance its text position.

This support applies to single-column sections. Frames containing unsupported drawings, notes, or revision structures retain ordinary layout. Frame groups that block the full text width and leave no vertical room on a fresh page also retain ordinary layout. The editor preserves all frame properties on save. There is no interface for creating, moving, or resizing text frames.

Headers also support bounded page-anchored text frames with numeric positions and widths. Adjacent paragraphs with identical direct frame properties share one frame. These frames retain paragraph borders and auto or minimum heights. They do not increase the header height that positions body text. Ordinary header content, including inline images, keeps its flow position.

This subset requires a separate ordinary paragraph and clear space around the frame. Headers with fields or revisions retain ordinary flow for this subset. Frames with exact heights, negative positions, overlapping content, or unsupported properties also retain ordinary flow. The editor preserves source paragraphs and their text positions.

### Tables

<FeatureMatrix category="tables" />

For fixed tables without a positive table width, explicit cell preferences can replace a wider initial grid. This applies when every cell has a positive absolute width and occupies one column. The largest preference in each column sets its width. Hidden revision rows prevent this replacement. Layout does not rewrite these properties when you save.

#### Table alignment

Files without a compatibility mode, and files in compatibility mode 11, 12, or 14, align the content of a top-level percentage-width table with the text column. The percentage is a share of the text-column width plus the outer cell margins that the table states. A left-aligned table puts the content of its first cell on the left text edge, moved by its indent. A right-aligned table puts the content of its last cell on the right text edge, and a centered table centers on the text column. A right-to-left table aligns from its leading edge in the same way. This applies to AutoFit and fixed tables, whatever width the authored grid states, in body, header, footer, text-box, and note stories. Floating tables, tables with cell spacing, and tables with uneven or unstated outer margins keep their existing geometry. A top-level table that states no usable width uses the same reference box. An AutoFit table without a width fits the room its leading indent leaves, in every compatibility mode. With neither a table style nor a stated indent, a left-aligned table puts its outer edge, not its content, on the text edge.

Outside that reference box, a percentage excludes the mean width of the table's simple outer side rules, and the table then adds that rule back. This applies to nested tables in every mode and to every table in compatibility mode 15 and later.

In that reference box, a cell margin narrower than half of a single outer side rule counts as half of that rule. A table with zero cell margins, with or without a percentage width, therefore also aligns its content with the text column. A percentage stated with a percent sign above 655.34% uses the same reference box. In a text box, the reference box for a percentage is 0.75 points wider, and a right-aligned table puts its outer edge, not its content, on the right edge of the text box. A nested AutoFit table without a usable width fits the content width of its cell plus its own outer cell margins.

An AutoFit table in which every column states an absolute preferred width starts from those widths. First, each column grows to hold its widest unbroken word. If the table is then wider than its room, or than its percentage share, each column gives up width in proportion to how far it is wider than that minimum. A percentage table that is narrower than its share grows each column in proportion to its width. Nested tables keep proportional scaling.

In compatibility mode 15 and later, a right-to-left table moves toward its visual left by half the mean width of its simple outer side rules.

A table percentage width can be larger than 100%, up to 655.34%. The table then extends past the text column and keeps its cells' line breaks. This applies to every alignment, to AutoFit and fixed tables, and in every compatibility mode. A nested table can extend past its cell in the same way. A supported full-width table in a file without a compatibility mode, or in compatibility mode 11, 12, or 14, measures the percentage against the text-column width plus its outer cell margins. A larger count of fiftieths wraps at 65536, and a count that wraps above 32767 states no width. A larger value stated with a percent sign makes the table as narrow as its content allows.

AutoFit widths account for deleted content across revision views. Each view retains the minimum widths its visible content requires.

An AutoFit column widens to hold its widest unbroken word, such as a long URL, with its indents and cell margins. Spaces at the start of a paragraph do not join the first word, because the word can start the next line. When the column has to widen anyway, it widens enough for that word to stay on the first line with its first-line indent. Files without a compatibility mode, and files in compatibility mode 11, 12, or 14, leave a first-line indent out of the column minimum: a word too wide for the indented first line breaks there. A cell with `w:noWrap` keeps its column at least as wide as the cell's preferred width, and its text still wraps. The table can then grow past its own width, up to the width of the text column or, for a table wider than the column, further. The other columns give up width in proportion to their spare room. When the minimums are wider than the text column, the columns shrink in proportion to their minimums to the wider of the text column and the table. A top-level AutoFit table with an absolute width wider than the text column, in any section column, is the exception: a narrower grid stretches to that width, and minimums wider than it widen the table, also past the page edge. Nested, fixed, text-box, and percentage-width tables keep the first rule.

In East Asian text, an AutoFit column measures its minimum width at legal line breaks, so a column of ideographs can narrow to a single character.

An AutoFit column whose cells state no width is sized by its content. Each such column takes its widest unwrapped line when the table has room, and the columns share any extra room in proportion to those widths. A table with no width of its own takes only what its content needs. Columns with a stated width give way first. When the table is still too narrow, the content-sized columns wrap, each by the same fraction of its range.

A cell that spans columns widens them to hold its widest unbroken word. The spanned columns share that width in proportion to their stated width plus their content, and the columns outside the span give up the difference. A nested fixed table needs only the content it holds, whatever its stated width, and paints no wider than its cell: its columns give way down to their own content. A nested AutoFit table also keeps its resolved width. Both keep their leading indent. A narrowed nested fixed table keeps the width its cells of vertical text have; elsewhere, cells with vertical text set no minimum.

Cell spacing applies on each side of every cell. Neighboring cells, and a cell and the table edge, sit twice the spacing apart, and the gaps come out of the table width.

With no compatibility mode, or in compatibility mode 11, 12, or 14, supported fixed tables align the first cell’s content with the table indent. This applies to left-aligned, top-level tables with automatic or absolute widths and no cell spacing. Each row must cover the grid and use the same leading cell margin. Simple side rules share the margin space when the margins clear half the rule. The column widths remain unchanged.

Nested, positioned, and right-to-left tables retain their existing geometry. Tables with row-level geometry exceptions also retain their existing geometry.

#### Tabs inside cells

In left-to-right table text without adjacent floating objects, an ordinary left tab can continue on the next line. This occurs when its next stop exceeds the cell line edge and visible content follows it. The tab keeps its source position and uses the next line’s tab stops. Paragraphs with consecutive tabs retain their existing placement. Trailing, aligned, and positional tabs also retain their existing placement.

#### Floating tables

Body text wraps beside supported floating tables and below tables that cover the text column. Text does not wrap into gaps of 0.25 inches or less beside floating tables. Captions and headings move past these gaps. The table's text distances keep the authored gap between its border and surrounding text. Text-anchored tables with numeric vertical offsets follow their next ordinary paragraph onto its page and column.

A page- or margin-anchored table that overlaps the text column and reaches below the bottom margin breaks across pages. It starts at its authored position, or higher so that the part that fits on the page ends at the bottom edge of the page. That part is the whole rows that fit and the lines of the next row that fit below them. The rest continues at the top of the next page. The text after the table continues on the page of the last part, as it does after a text-anchored table. In documents that use Word 2013 or later layout, the first part ends at the bottom margin. In earlier layout, only a table that reaches below the bottom edge of the page breaks, and its first part can reach that edge.

When a floating table pushes its own anchor paragraph past the bottom of the page or column, the table stays where it is and only the anchor moves on. Two floating tables with identical positions and no paragraph between them stack into one table: the second starts at the bottom of the first. Negative offsets remain in place when they clear preceding text. In a single-column section, a table that leaves no passage wider than 0.25 inches beside it also keeps its place over preceding text, and the lines it covers move below it. A narrower table that intersects preceding text moves below that text. At the top of a page, a negative offset can place the table in the top margin. A page-positioned or margin-positioned table also wraps the earlier text on its page. If it leaves no passage wider than 0.25 inches, the earlier lines it covers move below it. If those lines would push its anchor off the page, the anchor and the table start on the next page instead.

If a text-anchored table does not fit the space left on the page, it breaks across pages when that space holds its opening. The opening is the header rows and the first line of each cell in the first body row. If that row has a minimum height, the opening includes that height. If that row has an exact height, the opening is the whole row. A text-anchored table taller than a page also breaks. If the opening does not fit, the table moves to the next page and keeps its offset there. A table with a negative vertical offset that does not fit the space left also starts on the next page.

The first part of a breaking table keeps its offset below the preceding text. The rest continues at the top of the next page, below repeated header rows. Rows break as they do in a table without a position. A row splits between lines at the bottom of the page. It moves to the next page only when the space left cannot hold its minimum height or the first line of each cell. Rows split even when they are set not to break across pages.

The paragraph after the table, and the text after that paragraph, continue on the page of the last part. If the last part leaves no passage wider than 0.25 inches beside it, that text starts below the last part, after its text distance below. Space before the paragraph then applies below the table. Otherwise the text starts at the top of the page or column and wraps beside the last part, without space before. A page break or column break before the paragraph applies after the table. If an earlier floating table shares the paragraph, the earlier table stays where the body reached the breaking table.

The following conditions keep a text-anchored table whole, so that it moves with its following paragraph:

- The table has a text distance above it.
- The table has a negative vertical offset.
- The section has more than one column.
- The document enables `w:doNotBreakWrappedTables`.

These conditions do not apply to a table taller than a page, or to a table whose cells can wrap around earlier floating pictures or frames. They also do not apply when a header or footer has wrapping pictures. A table whose rows fit the space left stays whole, even when its text distance below does not fit. If the opening of a table placed in the flow fits neither the space left nor a fresh page, the table starts where it stands. Text-anchored tables that use vertical alignment retain their normal flow behavior.

A text-anchored table marked no-overlap floats like other tables, and text wraps around it. If it would cover an earlier floating table, it moves right of that table, so that their text distances touch. In compatibility mode 15 and later, it can also move left of that table. If neither side has room between the margins, it moves below that table. Floating tables without this setting can overlap one another. The cell text of a floating table placed at its anchor never wraps around another floating table.

A continuous section that starts on the same page wraps its text beside the floating tables and wrapping pictures of earlier sections on that page. An ordinary table that would cover a floating table starts below it. A narrower table stays beside it.

Before compatibility mode 15, a right-aligned floating table in the body moves right by the right cell margin of the table, so that its cell text ends at the frame edge. Simple tables can share a terminal empty paragraph without shrinking that paragraph or adding a blank page. The editor preserves floating-table properties when you save. There are no controls for editing those properties.

A floating table at the top level of a header or footer sits outside the story flow. In compatibility mode 15 and later, the header or footer text after it wraps beside it or moves below it, and the header or footer grows with that text. Body text wraps around the table on every page that shows that header or footer, in every compatibility mode. A page- or margin-anchored header or footer table keeps its page position and moves up onto the page when it would pass the bottom edge of the page. Footer text moves below such a table when the table ends above the bottom edge of the footer. When the table reaches past that edge, or when the text below it would pass the bottom edge of the page, the footer text moves above the table instead. Text that the table pushes down can extend past the bottom edge of the footer, but never past the bottom edge of the page. Footer text that wraps beside a narrow table grows the footer upward when it would pass the bottom edge of the page.

When you compare a multipage table, check the space between each repeated header and its first body row. The table pagination note lists the shared-border measurement limits. Keep the original document when you report a spacing issue.

### Text columns

A multi-column section balances its final page before a continuous section follows. Earlier pages retain their column distribution.

If settings enable `w:noColumnBalance` in a document saved in compatibility mode 14 or earlier, or with no declared mode, the section fills each column before the next. In compatibility mode 15 and later, the option has no effect and the section still balances. An absent flag or an explicit off value retains balancing. The following continuous section starts below the tallest column, even when balancing is disabled.

### Images and drawings

<FeatureMatrix category="images" />

A floating object in a table cell can turn off the **Layout in table cell** option. Word honors that setting only in compatibility mode 14 or earlier, or when the document declares no mode. The object is then placed against the page, unless it is positioned against its own character or line. If the object wraps text, intersecting table rows move below it. The object keeps its position. In compatibility mode 15 and later, Word ignores the setting and keeps the object in its cell.

Two other placement rules depend on the compatibility mode or the object options. Before compatibility mode 15, ordinary header and footer text ignores wrapping objects in the same header or footer. If an object must not overlap another object, Word moves it beside that object at the same height. The object moves down only when neither side has room.

## Layout and document settings

The editor calculates document layout without browser flow layout. It uses document fonts, themes, section geometry, margins, and Word units.

The layout result controls line and page breaks. The editor paints selectable DOM text from that result.

Document settings affect pagination as well as appearance. These settings include compatibility mode, paragraph keep rules, section line grids, and table row minimums. The feature notes identify the settings and limits for each behavior.

A valid compatibility mode declared directly under the settings element, outside `w:compat`, applies when `w:compat` holds no valid declaration. An invalid value there is ignored.

### Manual page breaks

Manual page breaks (`w:br w:type="page"`) inside table cells do not add lines, line height, or pages. This applies to breaks at the start, middle, or end of a cell paragraph. The text on each side of a break stays on the same line. Line wrapping, tab alignment, and text wrap around floating pictures treat the text as if the break were absent. The document retains these breaks for editing and saving. Manual line breaks still start a new line inside a cell.

A manual page break at the start of a paragraph moves its following text or page break to the next page. This also applies when the current page has no room for another line. The position before the break stays at the bottom of the current page. The text on the next page gets the space before of the paragraph, in every compatibility mode. Adjacent paragraph spacing follows the document’s spacing rules.

The preceding space after normally reduces this leading space. The space after of the text overlaps the space before of the next paragraph in the same way. In a numbered or bulleted paragraph, the number or bullet goes to the next page with the text.

This rule also applies to a paragraph with borders or shading. Lines that hold only page breaks draw no border. The text after the breaks starts a separate border box on the next page, including the paragraph’s top border. The preceding paragraph closes its border box with its bottom border. This happens only when the displayed paragraph starts with the break.

A hidden break does not separate the border group. This includes tracked changes hidden by the selected review view. Shading fills each break line where it sits, up to the page edge.

This rule does not apply to some paragraphs. A paragraph with only one page break, or with only hidden content after the break, keeps the ordinary rule. This includes a single break after a table that fills the page. A paragraph that opens with a page break followed by another page or column break keeps its first break on the current page. Each later break starts one more page. A paragraph that anchors a floating table, text frame, or drawing also keeps it. After a full page, its break line moves to a new page. Its text starts one page later.

A manual column break at the start of a paragraph stays at the bottom of a full page or column, even with nothing after it. The content after the break starts in the next column, or on the next page after the last column. That content gets the paragraph's space before and top border, as text after a leading page break does.

A page break directly followed by a line break does not start a new page. The line break still ends the line, so the text after it continues on the next line.

### Section boundaries

A continuous section can share the preceding section’s last page when its page size and orientation stay the same. A trailing page break in the preceding section starts the continued text on the next page. A shared page retains its header, footer, and text area, even if the following section uses different variants or heights. The following section’s header and footer start on the next page.

Odd-page and even-page sections can insert an empty sheet to reach the required page number parity. That sheet contains no header, footer, or document content. `NUMPAGES` includes it; `SECTIONPAGES` does not. The sections matrix note also explains page numbering restarts.

An empty paragraph that ends a section ignores its own page break before, from direct formatting or its style. It stays after the section's content, so it does not add a blank page. The next section's break type controls where that section starts. This rule does not apply when nothing comes before the paragraph in its section. It also does not apply when the paragraph holds text, a tab, hidden text, or a field. Bookmarks, proofing marks, permission markers, comment range markers, and empty text runs do not prevent this rule.

An empty paragraph that ends a section also stays on the page when its line does not fit the space left. It takes no space from a footnote area on that page. If the next section starts on a new page, that paragraph does not draw its borders or shading, and it does not start a page of its own.

### Table rows and merged cells

Bottom-to-top cell text does not make its row taller. The text wraps at the final row height, or along the full merged cell height. The cell width clips overflowing text.

A table row that closes a page reserves space for its bottom border. A following row that can split can keep the preceding row on the page.

A table row starts below other content only when the remaining space holds its minimum height, plus the rule that closes the page where the row splits. If it does not, the row moves to the next page, also when its content is taller than a page. A keep-with-next paragraph before the table moves with the row. If a fresh page cannot hold that minimum below repeated headers, the row splits where it stands. When a row with a minimum height splits, the part on the next page is at least as tall as that minimum. Positioned tables that break across pages apply the same rules to their rows.

A row with an exact height taller than the page content starts on a fresh page and does not split. It fills the rest of that page, and its border and content stop at the bottom margin. The row does not paint past the margin, with or without `w:cantSplit`. The next block starts on the next page.

Keep-with-next table groups include closed vertical merges. Their merged content contributes its height once across the covered rows. Table decisions measure at most 256 kept rows and the next row. Longer groups use that measured prefix as a lower bound. Paragraph keep lookahead remains unchanged.

Changes to numbering and document properties update field text and table pagination during editing.

Merges that enter or leave the measured group retain ordinary row placement. Active floating content also uses ordinary row placement when it changes the available width.

Fixed-height horizontal cells display the part of a line that starts inside their content box. A taller line does not enlarge the row. Text below the box stays in the document and does not continue on another page.

Vertical cell merges that cover the same rows share those rows without adding their heights twice. In fixed-height rows, a merged cell whose content fits the complete span displays all of it. If the content does not fit, the text flows through every row of the span and is clipped at the bottom of the last row. A line that starts inside the span shows its visible part. If a text-only span of three or more rows crosses a page, the part above the break shows whole lines, and the text continues in the rows on the next page. Some merges are still clipped at their first row: a merge that contains or partly overlaps another merge, a second, shorter merge that starts in the same row, and a two-row span that crosses a page.

### Fields and paragraph spacing

Saved results of fields inside another field's instruction do not add text, line breaks, or links. The outer field keeps its normal display behavior. Fields inside a saved result still display.

Named character styles set the font properties of empty paragraph marks and numbering markers. Direct mark properties override those styles. A mark's character style also sizes the empty line after a trailing line break. It does not enlarge a line that contains text or an inline picture. A direct mark size also leaves lines with text, inline pictures, or equations unchanged.

For lines containing only inline pictures, the picture runs set the text height. A line with superscript or subscript text keeps that text's full-size height above and below the baseline, on every line of the paragraph. A larger paragraph style size does not enlarge that line. When you type in an empty paragraph, the new text takes the character style of the paragraph mark.

Active section line grids set the height of automatically spaced body lines in whole grid steps. The space below the text in a grid line can extend past the bottom margin, so a line fits on a page when its text fits. Multiple line spacing counts in grid steps: a line takes the larger of the steps its text needs and the multiple, with the text centered. Minimum line spacing up to the grid step takes the grid step, and a larger minimum keeps its own height. Exact line spacing keeps its authored rule, and the whole line must fit. A paragraph can turn off snapping through direct formatting or an inherited style. Table cells snap only when the document enables `w:adjustLineHeightInTable`. Footnote and endnote text snaps to the grid of the section that holds it. Headers, footers, and text boxes do not snap.

Adjacent paragraph spacing normally uses the larger of the preceding space after and following space before. With `w:doNotUseHTMLParagraphAutoSpacing`, those values add together. That setting also changes automatic spacing to 5pt before and 10pt after. The rule applies in body text, table cells, headers, footers, notes, and text boxes.

### Fonts and text direction

Supply usable font bytes for accurate text measurement. For more information, see [Fonts and measurement](/docs/2.x/guides/fonts).

Known single-byte Symbol and Wingdings bullets use Unicode fallback when their font is unavailable. Layout still uses the line height and advance widths of the symbol font. The editor preserves the original numbering definition when you save.

No-break spaces (U+00A0, U+2007, and U+202F) retain their line-break behavior across formatting runs. This also applies to word joiners (U+2060 and U+FEFF). Ordinary spaces can still provide break positions. Oversized groups retain the existing overflow rules.

The configured font resolver also receives faces used by SYMBOL fields and numbering markers. Your host must supply usable font bytes for those faces when they are unavailable locally. Unused numbering definitions do not add font requests.

Paragraph `w:bidi` controls alignment and the order of groups with different run directions. Run `w:rtl` controls the directional context within each group. Unmarked numeric text such as `1 980` keeps its left-to-right order in right-to-left paragraphs. Arabic, Hebrew, and Arabic-Indic digits retain their Unicode direction within that context. Authored Unicode direction controls use paragraph-wide Unicode ordering. Selection and caret positions follow the displayed text without changing source offsets.

### Thai, Lao, Khmer, and Myanmar line breaking

Thai, Lao, Khmer, and Myanmar text puts no spaces between words. Lines in these scripts wrap at any character cluster that fits, not at dictionary word boundaries. Table AutoFit keeps an unspaced run of these scripts whole as one segment.

To mark a word boundary, insert a zero-width space (U+200B). A line can end after a zero-width space in any script, and the zero-width space stays at the end of that line. A space before a zero-width space counts as text while it fits on the line, so a right-aligned line ends one space short of the margin. The space hangs past the margin only when it does not fit. Inside a justified line, a space followed by a zero-width space stretches and compresses like any other space.

Line breaks never split a character cluster. A Khmer coeng or Myanmar virama keeps the consonant stacked under it on the same line. Myanmar vowel signs and the visarga, such as `ာ` and `း`, stay with their consonant. A word that starts with a vowel sign after a space, as in Zawgyi-encoded Myanmar, still breaks at the space.

In every script, a dash between letters is a break position even when the text after it starts a new run, so `ALPHA` followed by a run `-PRIME` can wrap after the dash.

### East Asian typography

East Asian layout keeps punctuation, graphemes, and full-width number groups together across formatting changes. Justified lines distribute inter-character spacing through the same geometry used for paint and caret placement.

Justified lines compare space compression with the expansion needed for an earlier break. Hyphenated fragments and currency or math symbols participate in this fit calculation. Plain `REF` results can complete a word; changing `PAGEREF` and `NOTEREF` results cannot.

Modern Latin justification includes terminal footnote and endnote citations when testing whether a complete word fits. Citations keep their formatting and model positions. Marks with reserved page-local widths retain their existing line-break behavior.

East Asian font hints select the document's East Asian face for supported punctuation, symbols, Greek, and Cyrillic ranges. Combining marks and joined emoji keep their base character's slot across text runs. Explicit symbol fonts retain their selected face.

Document settings control kinsoku, Japanese strict rules, Korean character wrapping, and punctuation overflow. Text that kinsoku keeps together, such as `3ヵ` under strict rules, moves to the next line as one unit. If that unit is wider than a whole line, it breaks at its last fitting character, like a long Latin word. The automatic spacing before each fragment counts toward the fit, and the spacing at the break is dropped. A justified line keeps the unit whole if it fits with its automatic spacing at half width. Adjacent full-width punctuation shares a half-cell bearing when both runs enable `w:kern` at their font size. `w:noPunctuationKerning` disables this compression. The East Asian face of the document defaults (`w:rPrDefault`) must be an East Asian font. A known Chinese, Japanese, or Korean font qualifies. A known Latin font, such as Arial, does not. Another face qualifies only when the font table gives it a Shift JIS, Hangul, GB2312, or Big5 `w:charset`. An East Asian theme font with an empty theme slot qualifies. Korean-language runs retain their advances. Close/open, close/close, open/open, comma/period, and colon/open pairs compress; open/close pairs do not. The run's own font, bold, italic, and authored tracking do not select the rule. Run boundaries do not disable it. Paragraph and manual line-break boundaries retain their advance widths. A pair compresses only when both characters are on the same line, so punctuation at the end of a line keeps its full advance. Punctuation overflow (`w:overflowPunct`) hangs line-end punctuation past the margin only in justified paragraphs. This applies to full-width punctuation and to Latin punctuation in a run with an East Asian language. Left-aligned, centered, and right-aligned lines keep line-end punctuation inside the margin. When a justified line needs more room than the hanging mark gives, the mark still hangs and the punctuation before it compresses for the rest. If the document defaults (`w:rPrDefault`) name no East Asian face, no punctuation hangs.

Table AutoFit sizes the minimum width of East Asian text at legal line breaks. A bracket or period that kinsoku keeps with an ideograph counts with that ideograph. When this pair rule compresses adjacent punctuation inside one unbreakable segment, the minimum uses the compressed width. For example, `字。」` needs two and a half ideographs, not three. A pair that a legal line break separates, such as `」「`, keeps both full advances. With `w:kinsoku` off, each mark stands alone at its full advance. The AutoFit maximum width, which keeps the paragraph on one line, uses the compressed width of every pair, including `」「`.

`w:characterSpacingControl` does not enable or disable this pair rule. Latin punctuation keeps the font's HarfBuzz kerning, including with `w:noPunctuationKerning`.

Run language uses `w:lang` elements and attributes in the WordprocessingML namespace across styles and direct formatting. Foreign language extensions remain saved but do not select the layout language.

Colons can compress before opening brackets, bounded by the following bracket's available bearing. With measured glyph bounds, colons also compress before closing punctuation. This pair rule halves the colon's advance, including authored character spacing. Other centered punctuation, authored spaces, outlined text, decorated text, and tracked changes retain their advances. Colons with highlight or shading retain their advances.

If wrapping separates a compressed colon from its opening bracket, the paragraph uses natural colon advances. Only justified paragraphs compress punctuation to fit a line, and only when the document defaults name an East Asian face. Left-aligned, centered, and right-aligned paragraphs wrap instead. Adjacent full-width punctuation pairs still compress at every alignment. Narrow plain left-to-right (LTR) justified East Asian paragraphs can compress punctuation to fit the next glyph and protected punctuation. Each closing mark and colon gives up to half its advance on its right side, and each opening mark on its left side, next to any glyph on the line. A closing mark or colon before an opening mark gives both sides, each up to half of the smaller glyph. The shrink goes in equal shares to every blank side, and a side that runs out passes the rest to the others. The next glyph joins the line only when the share of this capacity that it uses is no larger than the expansion that leaving it off would need. That expansion counts in 1/64 of each advance before the line's last glyph. A final mark that hangs, or that gives up its trailing half, counts toward this capacity, and its advance stays in the compression that the glyph needs. For example, at 12 pt two blank sides let a five-glyph line take 11.4 pt of compression, and a fifteen-glyph line about 10 pt. Fitting uses measured glyph bounds and preserves source positions. Later Latin text does not disable fitting on an earlier qualified East Asian line. Supported mixed lines can share the measured external ink bearing of a complete Latin word, digit group, or ASCII symbol group with adjacent East Asian punctuation. Only the East Asian punctuation loses advance; Latin words, ligatures, digits, and curly quotes without the East Asian font hint retain their measured widths and source ranges. In runs with `w:hint="eastAsia"`, a curly quote can lose up to half its advance on its outer side, on a line that also contains East Asian punctuation. The outer side can face an East Asian character, punctuation, or a Latin word. A closing quote that ends a fitted line loses its trailing half after any glyph. A colon or closing mark before an opening quote gives both blank sides. A colon before a quote without the hint gives its own side. This local path requires resolved faces, punctuation kerning that the document settings allow, an East Asian document-default face, and no authored character spacing or horizontal scaling. A word boundary needs its complete shaped outline; absent or invalid outlines cannot use the advance box as a substitute. Unknown scripts, fields, decorations, revisions, right-to-left (RTL) text, and complex shaping retain conservative fitting. So do gaps beside floating objects and measurers without ink bounds.

Kana uses deterministic advance reductions.

The document's `w:themeFontLang` selects supplemental theme fonts for its Latin, East Asian, and complex-script theme tokens. The resolver reads `val`, `eastAsia`, and `bidi` independently. It supports CJK languages, common complex-script languages, and explicit script subtags. Complex-script theme tokens also work on Latin font attributes. When no inherited or direct Latin font reference exists, the resolved body Latin theme supplies the default.

When no style supplies an East Asian face, a resolved body East Asian theme face supplies the default. When the East Asian theme language is absent and its face is empty, inherited `w:lang/@w:eastAsia` selects the supplemental face. Chinese, Japanese, and Korean use named CJK defaults when neither the theme nor the run supplies a face. Word's default language can depend on its installation language and keyboards. Font resolvers receive the selected candidates before shaping.

Supply suitable fonts for matching glyph metrics.

The feature matrix lists the support limits for East Asian typography.

For pipeline details, see [Architecture](/docs/2.x/core/architecture). Test your documents in the [live demo](https://docx-editor.dev/editor).

## Round-trip contract

A DOCX file is a ZIP package with XML parts and binary payloads.

| Content | Save behavior |
| --- | --- |
| Modeled OOXML | Serializes from typed document nodes. |
| Unmodeled XML elements and attributes | Re-emits generic nodes in place. |
| Legacy VML, custom XML, and add-in markup | Preserves structural content. |
| Media, VBA projects, embedded fonts, and OLE binaries | Copies package payloads without modification. |
| Relationship IDs, bookmark names, style IDs, and numbering definitions | Keeps references intact. |
| Tracked changes | Writes Word `w:ins` and `w:del` revisions. |
| Theme colors | Keeps theme references instead of flattening them to RGB values. |

The contract protects semantic meaning and structure. It does not promise byte identity for rewritten XML parts.

An `xml:space="preserve"` attribute on a run does not turn indentation into document text. Spaces inside text elements remain authored text.

The editor preserves `w:br` and `w:cr` elements outside runs, directly inside paragraphs or hyperlinks. Save retains their position. The paragraph and its runs still render and stay editable. The misplaced break does not start a new line or page. A `w:tab` or `w:t` directly inside a paragraph, outside a run, still makes the whole paragraph unknown content. That paragraph and its text are kept on save, but the paragraph does not render and you cannot edit it.

Continuous integration checks real documents with a canonical tree fingerprint and a save-and-reopen semantic digest. Focused tests cover revisions, fields, hyperlinks, content controls, and browser editing.

If untouched content is lost or reinterpreted, report a [round-trip issue](https://github.com/eigenpal/docx-editor/issues/new/choose) with the source document.

## Security and data flow

| Concern | Behavior |
| --- | --- |
| Browser uploads | The editor package does not upload documents or call a conversion service. |
| Macros | The editor preserves VBA payloads but never executes them. |
| OLE | The editor preserves OLE payloads without running them. Supported inline objects display their cached preview picture. |
| Calculated fields | Supported calculated fields update display text only. Macros, DDE, and external includes remain inert. |
| Hyperlinks | Allowlisted targets open only after a user gesture. |
| Server editing | Your host controls where DOCX data runs. |
| Browser automation | Controls an editor already in the page. |
| External artificial intelligence | `@docx-editor.dev/editor-api` includes no model integration or transport. |

Your application controls any data sent to another service or model.
