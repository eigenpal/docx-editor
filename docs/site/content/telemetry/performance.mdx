---
title: 'Measure performance'
description: 'Record how fast the editor responds: input delay from key press to screen, and engine layout and paint time, as one summary per minute.'
category: 'Telemetry'
---

<Callout>`@docx-editor.dev/telemetry` is available in version 2.29.0 and later.</Callout>

The `performance` area reports how fast the editor responds to the person who uses it.

The editor collects timings and sends one `performance` event for each minute of use. It also sends one when the page is hidden and when the editor is destroyed. It never sends one event for each key press.

Each event has up to three timing summaries:

- `interaction`: the time from a key press or a pointer press on the pages to the next frame on screen. This is the delay that a person feels when they type or click. Presses that wait behind slow work count with their full delay. Presses of modifier keys alone, and presses while the page is hidden, are not timed.
- `layout`: the main-thread time of each engine layout pass that the person causes, by an edit or a view change such as zoom. A pass includes its background work, and the work of a pass that a newer edit replaced. Layouts that loading causes are not included: the opening layout, which the `document.open` event reports, and layouts after fonts or images arrive.
- `paint`: the time of each engine paint of the pages.

Each summary has `count`, `p50Ms`, `p95Ms`, `maxMs`, and `bands`, the number of timings up to 16, 33, 50, 100, 200, 500, and 1000 ms, and over 1000 ms. The event also has `windowMs` and `pagesBucket`. It has no keys, positions, or text.

If at least 20 presses were timed and more than one in 20 took over 200 ms, the event has the code `performance.slow-interaction` and a hint. The console exporter prints it as a warning, and the Sentry exporter records it as a warning breadcrumb, never as an issue.

The following example sends the performance events of about one editor in ten. The choice is made once for each editor, so one person's summaries stay together. Every editor with the area on still measures, and the metrics count every summary: sampling limits only the events, such as span events and breadcrumbs. To stop measuring, set `sampleRate` to 0.

```ts
import { createTelemetry } from '@docx-editor.dev/telemetry';
import { otelExporter } from '@docx-editor.dev/telemetry/otel';

export const telemetry = createTelemetry({
  exporters: [otelExporter()],
  include: { performance: { sampleRate: 0.1 }, documentOpen: true, trackedChanges: true },
});
```

Sampling applies to events only, and a `sampleRate` of 0 turns performance measuring off, metrics included. The metrics `docx_editor_editor_interaction_duration_seconds`, `docx_editor_editor_layout_duration_seconds`, and `docx_editor_editor_paint_duration_seconds` count every summary. Their `pages` label is the page count bucket, one of `0`, `1`, `2-9`, `10-99`, `100-999`, and `1000+`, or `unknown` before the first paint, so you can compare documents of different sizes. Their bucket counts are exact, and their sums are estimated from the bands. For more information, see [Metrics](/docs/2.x/telemetry/metrics).

To watch editor performance in Prometheus, start from the following queries. The first gives the 95th percentile of input delay, key presses and clicks together, for each page count bucket. The second gives the share of presses that took over 200 ms:

```text
histogram_quantile(0.95, sum by (le, pages) (rate(docx_editor_editor_interaction_duration_seconds_bucket[10m])))

1 - sum(rate(docx_editor_editor_interaction_duration_seconds_bucket{le="0.2"}[10m]))
  / sum(rate(docx_editor_editor_interaction_duration_seconds_count[10m]))
```

If the share of slow presses grows, compare the layout and paint histograms for the same page bucket. Slow layout follows document size. Slow paint follows the pages on screen.

Send performance to an exporter that records metrics, such as `otelExporter()`. In a browser, the metrics reach Prometheus through your OpenTelemetry SDK and an OpenTelemetry Protocol (OTLP) collector; `prometheusRegistry()` serves metrics from a server process, not from a browser. The Sentry exporter records a performance event only as a breadcrumb, which Sentry shows beside a later error. A `callbackExporter` with an `onMetric` function receives each timing in a summary as one histogram sample, at the middle of its band.

The editor measures only while something wants the data: `telemetry.module` with the `performance` area on and consent given, another module whose `wantsDiagnostic` returns `true` for `'performance'`, or an `editor.on('diagnostic')` handler.
