Compare documents records the differences between an original document and a revised document as tracked changes. Accept all changes to get the revised document. Reject all changes to get the original text and its formatting. Some differences have no tracked form, so they stay after a reject: style definitions, content control properties, comments, and empty headers, footers, notes, and parts that inserted content brought. If you turn formatting detection off, the result takes the revised formatting without tracked changes, so rejecting all changes gives the original text with the revised formatting.

Compare documents requires an EigenPal Pro License. The editor command and `Document.compareFromBase64` also require the review module. Without it, they refuse with a stable reason. Follow [Tracked changes](/docs/2.x/pro/tracked-changes) to enable review features. The `compareDocuments` function needs no module.

You can compare documents in three ways:

- In the editor, from **Compare documents** in the **Review** menu, or with the `compareDocuments` command.
- With `Document.compareFromBase64` in the Office.js-compatible document API, on a server or in the browser.
- With the `compareDocuments` function from `@docx-editor.dev/pro`, which takes two DOCX files and returns a third.

## What a compare records

The compare aligns the two documents block by block, then compares matched text word by word. It records these differences:

- Inserted and deleted text, paragraphs, table rows, tables, images, and text boxes.
- Moved paragraphs, as move revisions at the source and the destination.
- Character, paragraph, table, and section formatting, when formatting detection is on.
- Changes in headers, footers, footnotes, and endnotes. Headers and footers compare section by section.

Block content controls follow the same rules as other content. A control that only one document has is kept, and its content is recorded as inserted or deleted. When accepting or rejecting removes all of its content, an empty control with placeholder text stays. Control properties keep no record, so the result takes the revised document's control properties.

Inline content controls follow the same rules. A control with the same ID in both documents is the same control, for example a form field that the revised document fills in. Its unchanged text stays, and it takes the revised properties. Rejecting changes does not restore the original properties, so a placeholder that the revised document fills in shows its text as ordinary text after a reject. When equal text sits in two different controls, smart tags, or custom XML elements, the result records it as deleted from one and inserted into the other.

The compare runs on both documents with their existing tracked changes accepted. The result keeps the comments of both documents. Bookmarks and header and footer references come from the original. A style that both documents define takes the revised definition, so revised content looks as it does in the revised document. Rejecting changes does not restore the original style definitions. Lists keep the original's definitions, and the styles and lists that only the revised document defines are added. Field results are compared as saved; the compare never updates or runs fields.

## Compare in the editor

Add `reviewModule()` to the editor modules. The **Review** menu then shows **Compare documents**. The dialog asks for the revised DOCX file, the author name for the revisions, and whether to detect formatting changes. The open document is the original.

The differences replace the open document's content as one undoable step. One undo restores the original. When the documents have no differences, the document, its undo history, and its saved state stay as they were.

For example, two documents of about 500 pages each, with every paragraph changed, compare in one to two seconds. A compare accepts at most about 100,000 blocks, or 3 million characters, in both documents together. Blocks are paragraphs, table rows and cells, styles, and list definitions. Characters are UTF-16 code units, and each run also counts as 12 characters. Larger documents refuse with `tooLarge`.

After a compare that changes the document, the dialog closes and the editor announces the number of recorded changes to screen readers. When the documents have no differences, or the compare is refused, the dialog stays open and shows the message.

### Compare in a worker

By default, the dialog compares on the page's main thread. The page does not respond until the compare ends, and a running compare cannot be canceled. To compare in a worker, pass a function that starts the compare worker, `@docx-editor.dev/pro/compare-worker`, as the `compareWorker` option. The dialog then shows a progress bar with the running step, the page stays responsive, and **Cancel** stops a running compare and leaves the document unchanged.

The following sample starts an editor that compares in a worker. It imports the worker with the `?worker` suffix of Vite:

```ts
import { createDocxEditor } from '@docx-editor.dev/core/editor';
import { reviewModule } from '@docx-editor.dev/pro';
import CompareWorker from '@docx-editor.dev/pro/compare-worker?worker';

const editor = createDocxEditor({
  document: originalBytes,
  modules: [reviewModule({ compareWorker: () => new CompareWorker() })],
});
editor.attach(container);
```

The editor starts one worker for each compare and ends it when the compare ends. While the worker runs, the main thread only copies the open document and applies the result. The `compareDocuments` command stays synchronous and always compares on the main thread.

If the worker fails before it starts, for example because a deploy removed its script while the page stayed open, the dialog compares on the main thread instead. A worker that fails after it starts ends the compare with the `failed` code.

A compare in a worker can end with two codes of its own:

- `documentChanged`: the open document changed while the compare ran, so the result is not applied. The editor never compares again by itself; compare again to get a result for the current document.
- `busy`: another compare of the same dialog runs, or a preview or an external document refresh blocks edits. Try again when it ends.

### Compare from your own interface

If your application already has the revised bytes and wants worker progress and cancel, open the dialog session from your own interface. This is the supported way to run a compare in the background without the packaged dialog:

1. Register chrome with `editor.setCompareDocumentsChrome({ onRequest })`. The editor then passes each dialog session to `onRequest` instead of showing its own dialog.
1. Open a session with `editor.exec({ type: 'openCompareDocumentsDialog' })`.
1. Call `session.apply(request, { onProgress })`. With the compare worker, `onProgress` receives each step.
1. Call `session.cancel()` to stop a running compare, or to close a session that stays open after a refusal or a compare with no differences.
1. Call the function that `setCompareDocumentsChrome` returns when your interface no longer handles compares.

The following sample compares bytes that your application holds and shows each step:

```ts
import {
  compareDocumentsErrorKey,
  type CompareDocumentsDialogSession,
} from '@docx-editor.dev/core/editor';

let session: CompareDocumentsDialogSession | null = null;
const dispose = editor.setCompareDocumentsChrome({
  onRequest: (next) => {
    session = next;
  },
});

async function compareInBackground(revised: Uint8Array) {
  const opened = editor.exec({ type: 'openCompareDocumentsDialog' });
  const current = session;
  if (!opened.ok || !current) return;
  showCancel(current.cancelable, () => current.cancel());
  const outcome = await current.apply(
    { revised, authorName: 'Legal' },
    {
      onProgress: ({ phase, fraction }) =>
        showProgress(t(`compareDocuments.phases.${phase}`), fraction),
    }
  );
  if (!outcome.ok) showMessage(t(compareDocumentsErrorKey(outcome)));
  else if (!outcome.changed) showMessage(t('compareDocuments.noDifferences'));
  // A compare that changes the document closes its session; the others stay open.
  current.cancel();
}

// When your interface no longer handles compares:
dispose();
```

A second `apply` call while a compare runs answers `busy` and starts nothing. A `cancel()` call during a compare in a worker makes `apply` answer `closed`.

### Compare with the command

To compare without the dialog, for example from your own file picker, run the `compareDocuments` command:

```ts
import { compareDocumentsErrorKey } from '@docx-editor.dev/core/editor';

const result = editor.exec({
  type: 'compareDocuments',
  revised: revisedBytes,
  authorName: 'Legal',
  detectFormatChanges: true,
});
const outcome = result.compareDocuments;
if (!outcome?.ok) {
  showMessage(t(compareDocumentsErrorKey(outcome ?? { code: 'failed' })));
} else if (!outcome.changed) {
  showMessage(t('compareDocuments.noDifferences'));
}
```

The result's `compareDocuments` field holds the outcome of every `compareDocuments` command. A refused compare carries a `code`, such as `tooLarge` or `protected`, and for `unsupportedContent` a `reason`. The `compareDocuments.errors.*` and `compareDocuments.reasons.*` keys of `@docx-editor.dev/i18n` translate them, and `compareDocumentsErrorKey` picks the right key. A successful compare reports `changed` and `revisionCount`:

- `changed` is `false` when the documents have no differences. Nothing is recorded.
- `revisionCount` counts review items, as `revisions` collections and the review pane list them, in the body, headers, footers, and notes. A replaced word counts a deletion and an insertion.
- `changed` is `true` with a `revisionCount` of 0 when the only differences take no tracked change: formatting with detection off, style definitions, or the original's own tracked changes, which a compare accepts.

A background engine, the `compareDocumentsInBackground` contribution of a review module, returns a `CompareDocumentsBackgroundResult`. Its `bytes` are `null` when the documents have no differences. Read `changed`, not `bytes`, to decide whether to apply or save the result.

If you omit `authorName`, the revisions carry the editor's author. If the editor has no author, they carry the revised document's last author.

The command refuses while the editor is in viewing mode or the document is protected against edits. It refuses with `busy` while a preview or an external document refresh blocks edits. It also refuses while a collaboration session is attached, even when no one else is connected.

To replace the dialog, pass a component as `popups.compareDocuments`. The session's `apply` result has the same outcome shape. With the compare worker, pass `onProgress` as the second argument of `apply` to get each step, and check `cancelable` to know whether `cancel()` can stop a running compare. Its `message` is diagnostic English, not display text. Use `COMPARE_DOCUMENTS_ACCEPT` from `@docx-editor.dev/core/editor` as the `accept` value of your file input. For more information, see [Customize dialogs](/docs/2.x/customization/dialogs).

## Compare with the document API

`Document.compareFromBase64` follows the Office.js signature. Register `reviewModule()` on the runtime, then call the method with the revised document as base64 data:

```ts
import { DocxEditor } from '@docx-editor.dev/editor-api';
import { reviewModule } from '@docx-editor.dev/pro';

const runtime = await DocxEditor.createServer(originalBytes, {
  modules: [reviewModule()],
});
await runtime.run(async (context) => {
  context.document.compareFromBase64(revisedBase64, { authorName: 'Legal' });
  await context.sync();
});
const redline = await runtime.save();
```

For supported options and refusals, see [Compare two documents](/docs/2.x/editor-api/revisions#compare-two-documents).

## Compare two files on a server

The `compareDocuments` function needs no editor or runtime. It returns the result as DOCX bytes. When the documents have no differences, `changed` is `false` and `bytes` are the original bytes:

```ts
import { writeFile } from 'node:fs/promises';
import { compareDocuments } from '@docx-editor.dev/pro';

const result = compareDocuments(originalBytes, revisedBytes, {
  authorName: 'Legal',
  detectFormatChanges: true,
});
if (!result.ok) console.error(result.code, result.message);
else if (result.changed) await writeFile('redline.docx', result.bytes);
```

The function checks every result before it returns it: accepting all changes must give the revised text, and rejecting all changes must give the original text. A result that fails the check is not returned; the function refuses with `unsupportedContent` instead. It refuses with `invalidOriginal` or `invalidRevised` for a file it cannot read, with `tooLarge` for documents over its size limit, and with `invalidOptions` for an option of the wrong type, such as a `date` that is not a valid date. If you omit `authorName`, or it is empty, the revisions carry the revised document's last author. The function refuses with a code and never throws for these cases. An `unsupportedContent` refusal also names its `reason`. To translate a refusal, pass it to `compareDocumentsErrorKey` and use the key with `@docx-editor.dev/i18n`, as the editor does.

The function refuses with `protected` when the original document enforces protection that a compare would break:

- Read-only, comments, or forms protection. A compare would rewrite its content.
- Tracked-changes protection. Besides tracked changes, a compare writes differences that have no tracked form, such as style definitions, content control properties, comments, and the parts that inserted pictures need. Rejecting changes cannot take those back.

To compare a protected document, stop the protection first.

The compare also refuses with `unsupportedContent` in these cases:

- The documents differ inside a content control that is locked or bound to custom XML data. Tracked changes there cannot be accepted or rejected.
- The original or the revised document holds tracked changes that cannot be accepted, so its final state is unknown.
- The documents differ in block content that has no tracked-change form, such as an embedded file chunk, or a bookmark or content control around table rows and cells.
- The documents differ in a simple field with field data. The field keeps no record of its data, and its shell stays after its content is rejected.
- The revised document adds a section or table setting, such as page borders, that has no value a tracked change can restore on reject.
- A header or footer that only an earlier section shows differs, and the compare cannot pair it with one header or footer of the original. This happens when the documents have a different number of sections, and when the revised document splits a header or footer that sections of the original share.
- An earlier section of the revised document shows its own header or footer where the original's section inherits one from the section before it. Rejecting the change would show an empty header or footer there.
- The result needs a new relationship part, and the original document declares no content type for relationship parts.

An `unsupportedContent` refusal also carries a `reason` that names its case: `lockedContent`, `unresolvedRevisions`, `untrackedContent`, `unrecordedSettings`, `headerFooter`, `packageStructure`, or `unverified`. The dialog shows the message for the reason when there is one, else the message for the code. The `compareDocuments` command and `compareDocuments()` return both. If you build your own dialog, `compareDocumentsErrorKey(outcome)` gives the `@docx-editor.dev/i18n` key of that message:

```ts
import { compareDocumentsErrorKey } from '@docx-editor.dev/core/editor';

const outcome = await session.apply({ revised });
if (!outcome.ok) setError(t(compareDocumentsErrorKey(outcome)));
```

`Document.compareFromBase64` rejects `context.sync()` with a stable error code instead of the message: `NotImplemented` for these refusals and for `protected`, `InvalidArgument` for a revised file it cannot read, and `NotSupported` for documents over the size limit. The error's `debugInfo.innerError.code` names the cause, such as `edit.protected-content` or `edit.unsupported-content`.
