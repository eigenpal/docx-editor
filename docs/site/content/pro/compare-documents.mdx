Compare documents records the differences between an original document and a revised document as tracked changes. Accept all changes to get the revised document. Reject all changes to get the original. If you turn formatting detection off, the result takes the revised formatting without tracked changes, so rejecting all changes gives the original text with the revised formatting.

Compare documents requires an EigenPal Pro License. The editor command and `Document.compareFromBase64` also require the review module. Without it, they refuse with a stable reason. Follow [Tracked changes](/docs/2.x/pro/tracked-changes) to enable review features. The `compareDocuments` function needs no module.

You can compare documents in three ways:

- In the editor, from **Compare documents** in the **Review** menu, or with the `compareDocuments` command.
- With `Document.compareFromBase64` in the Office.js-compatible document API, on a server or in the browser.
- With the `compareDocuments` function from `@docx-editor.dev/pro`, which takes two DOCX files and returns a third.

## What a compare records

The compare aligns the two documents block by block, then compares matched text word by word. It records these differences:

- Inserted and deleted text, paragraphs, table rows, tables, images, and text boxes.
- Moved paragraphs, as move revisions at the source and the destination.
- Character, paragraph, table, and section formatting, when formatting detection is on.
- Changes in headers, footers, footnotes, and endnotes. Headers and footers compare section by section.

The compare runs on both documents with their existing tracked changes accepted. The result keeps the comments of both documents. Bookmarks and header and footer references come from the original. Styles and lists keep the original's definitions, and the styles and lists that only the revised document defines are added. Field results are compared as saved; the compare never updates or runs fields.

## Compare in the editor

Add `reviewModule()` to the editor modules. The **Review** menu then shows **Compare documents**. The dialog asks for the revised DOCX file, the author name for the revisions, and whether to detect formatting changes. The open document is the original.

The differences replace the open document's content as one undoable step. One undo restores the original. When the documents have no differences, the document, its undo history, and its saved state stay as they were.

The compare runs on the page's main thread. Documents of a few hundred pages take up to a few seconds, and the dialog shows that it is busy. A running compare cannot be canceled. The largest documents a compare accepts, about 100,000 paragraphs, table rows and cells, styles, and list definitions, or 1.5 million characters, in both documents together, can take about ten seconds. Larger documents refuse with `tooLarge`.

```ts
import { createDocxEditor } from '@docx-editor.dev/core/editor';
import { reviewModule } from '@docx-editor.dev/pro';

const editor = createDocxEditor({ document: originalBytes, modules: [reviewModule()] });
editor.attach(container);
```

To compare without the dialog, for example from your own file picker, run the `compareDocuments` command:

```ts
const result = editor.exec({
  type: 'compareDocuments',
  revised: revisedBytes,
  authorName: 'Legal',
  detectFormatChanges: true,
});
const outcome = result.compareDocuments;
if (!outcome?.ok) {
  showMessage(t(`compareDocuments.errors.${outcome?.code ?? 'failed'}`));
} else if (!outcome.changed) {
  showMessage(t('compareDocuments.noDifferences'));
}
```

The result's `compareDocuments` field holds the outcome of every `compareDocuments` command. A refused compare carries a `code`, such as `tooLarge` or `protected`. The `compareDocuments.errors.*` keys of `@docx-editor.dev/i18n` translate every code. A successful compare reports `changed` and `revisionCount`:

- `changed` is `false` when the documents have no differences. Nothing is recorded.
- `revisionCount` counts revision elements, not review items. A replaced word counts a deletion and an insertion.
- `changed` is `true` with a `revisionCount` of 0 when the only differences take no tracked change: formatting with detection off, or the original's own tracked changes, which a compare accepts.

If you omit `authorName`, the revisions carry the editor's author. If the editor has no author, they carry the revised document's last author.

The command refuses while the editor is in viewing mode or the document is protected against edits. It also refuses while a collaboration session is attached, even when no one else is connected.

To replace the dialog, pass a component as `popups.compareDocuments`. The session's `apply` result has the same outcome shape. Its `message` is diagnostic English, not display text. Use `COMPARE_DOCUMENTS_ACCEPT` from `@docx-editor.dev/core` as the `accept` value of your file input. For more information, see [Customize dialogs](/docs/2.x/customization/dialogs).

## Compare with the document API

`Document.compareFromBase64` follows the Office.js signature. Register `reviewModule()` on the runtime, then call the method with the revised document as base64 data:

```ts
import { DocxEditor } from '@docx-editor.dev/editor-api';
import { reviewModule } from '@docx-editor.dev/pro';

const runtime = await DocxEditor.createServer(originalBytes, {
  modules: [reviewModule()],
});
await runtime.run(async (context) => {
  context.document.compareFromBase64(revisedBase64, { authorName: 'Legal' });
  await context.sync();
});
const redline = await runtime.save();
```

For supported options and refusals, see [Tracked changes](/docs/2.x/editor-api/revisions).

## Compare two files on a server

The `compareDocuments` function needs no editor or runtime. It returns the result as DOCX bytes. When the documents have no differences, `changed` is `false` and `bytes` are the original bytes:

```ts
import { writeFile } from 'node:fs/promises';
import { compareDocuments } from '@docx-editor.dev/pro';

const result = compareDocuments(originalBytes, revisedBytes, {
  authorName: 'Legal',
  detectFormatChanges: true,
});
if (!result.ok) console.error(result.code, result.message);
else if (result.changed) await writeFile('redline.docx', result.bytes);
```

The function checks every result before it returns it: accepting all changes must give the revised text, and rejecting all changes must give the original text. A result that fails the check is not returned; the function refuses with `unsupportedContent` instead. It refuses with `invalidOriginal` or `invalidRevised` for a file it cannot read, with `tooLarge` for documents over its size limit, and with `invalidOptions` for an option of the wrong type, such as a `date` that is not a valid date. If you omit `authorName`, or it is empty, the revisions carry the revised document's last author. The function refuses with a code and never throws for these cases. Translate a code with the same `compareDocuments.errors.*` keys the editor uses.

The function refuses with `protected` when the original document enforces protection that a compare would break:

- Read-only, comments, or forms protection. A compare would rewrite its content.
- Tracked-changes protection, when the original holds tracked changes. A compare would accept them.
- Tracked-changes protection, when formatting detection is off. A compare would write formatting differences without tracked changes.

With tracked-changes protection, no tracked changes in the original, and formatting detection on, the compare runs, because it writes only tracked changes.

The compare also refuses with `unsupportedContent` in these cases:

- The documents differ inside a content control that is locked or bound to custom XML data. Tracked changes there cannot be accepted or rejected.
- The original or the revised document holds tracked changes that cannot be accepted, so its final state is unknown.
- The documents differ in block content that has no tracked-change form, such as an embedded file chunk, or a bookmark or content control around table rows and cells.
- The documents differ in the properties of a content control, smart tag, custom XML element, or simple field with field data, or only one document has a block content control. These elements keep no record of their properties, and their shell stays after their content is rejected.
- The revised document adds a section or table setting, such as page borders, that has no value a tracked change can restore on reject.
- A header or footer that only an earlier section shows differs, and the compare cannot pair it with one header or footer of the original. This happens when the documents have a different number of sections, when an earlier section of the revised document shows a header or footer that the original's section lacks, and when the revised document splits a header or footer that sections of the original share.
- The result needs a new relationship part, and the original document declares no content type for relationship parts.

The dialog shows the message for the refusal code, and the `compareDocuments` command returns the code. `Document.compareFromBase64` rejects `context.sync()` with a stable error code instead of the message: `NotImplemented` for these refusals and for `protected`, `InvalidArgument` for a revised file it cannot read, and `NotSupported` for documents over the size limit. The error's `debugInfo.innerError.code` names the cause, such as `edit.protected-content` or `edit.unsupported-content`.
