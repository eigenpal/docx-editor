Collaboration has its own format version, separate from the package version. It decides which clients, servers, and workers can share a room. Ordinary DOCX files never need a collaboration upgrade.

- Compare the complete imported `COLLABORATION_FORMAT_VERSION`. Package versions do not establish room compatibility, and a minor release can require a migration, marked `Breaking collaboration upgrade`.
- Never construct the value, compare parts of it, or rewrite stored version metadata. Changing it does not convert data.
- Check clients before synchronization, and saved rooms separately before loading.

The four numbers of a value such as `docx-collaboration:1.5.3.1` identify the synchronization rules, storage structure, conflict-repair rules, and document model.

## Check clients before synchronization

Send the imported format version unchanged with your connection request. For Hocuspocus, encode it with the access token in a token callback:

```ts
import { COLLABORATION_FORMAT_VERSION } from '@docx-editor.dev/pro/collaboration';

// Implement this with your application's access-token service.
declare function fetchAccessToken(): Promise<string>;

export const token = async (): Promise<string> =>
  JSON.stringify({
    token: await fetchAccessToken(),
    collaborationVersion: COLLABORATION_FORMAT_VERSION,
  });
```

Pass `token` to `useHocuspocusCollaboration` or `connect`. The provider calls it on each reconnection and sends the string unchanged.

On the server, authenticate access, then check the version, before synchronization:

```ts
import { Server } from '@hocuspocus/server';
import {
  assertCollaborationFormatCompatibility,
  CollaborationSchemaError,
} from '@docx-editor.dev/pro/collaboration';

// Implement these with your authentication service and document permissions.
// `parseConnectionToken` throws 'Invalid credentials' on malformed input.
declare function parseConnectionToken(token: string): {
  token: string;
  collaborationVersion?: unknown;
};
declare function verifyDocumentAccess(accessToken: string, documentId: string): Promise<void>;

const server = new Server({
  async onAuthenticate({ token, documentName }) {
    const request = parseConnectionToken(token);
    await verifyDocumentAccess(request.token, documentName);
    try {
      assertCollaborationFormatCompatibility(request.collaborationVersion);
    } catch (error) {
      if (error instanceof CollaborationSchemaError) {
        // Hocuspocus forwards `reason` to the refused client.
        throw Object.assign(new Error(error.code), { reason: error.code });
      }
      throw error;
    }
  },
});
```

- Only an exact match passes. Other values throw `CollaborationSchemaError` with `collaboration-format-mismatch`.
- The Hocuspocus provider passes recognized server codes through. Handle `error.code`; do not parse messages.
- A version claim does not authenticate a client or prove which code it runs.
- Run the same checks in a custom provider's admission flow. WebRTC has no admission server, so control invitations and deploy compatible clients everywhere.
- `DOCUMENT_COLLABORATION_VERSIONS` and `assertDocumentCollaborationCompatibility` are deprecated but supported.

## Check saved rooms before loading

Validate a saved snapshot in a separate prepared document, then load it into the live room:

```ts
import * as Y from 'yjs';
import {
  assertCollaborationFormatCompatibility,
  readCollaborationFormatVersion,
  readCollaborationDocument,
  prepareCollaborationServerDocument,
} from '@docx-editor.dev/pro/collaboration';

export function loadRoom(live: Y.Doc, snapshot: Uint8Array): void {
  const candidate = new Y.Doc();
  try {
    prepareCollaborationServerDocument(candidate);
    Y.applyUpdate(candidate, snapshot);
    assertCollaborationFormatCompatibility(readCollaborationFormatVersion(candidate));
    readCollaborationDocument(candidate); // Validates that a complete DOCX exports.
    Y.applyUpdate(live, snapshot);
  } finally {
    candidate.destroy();
  }
}
```

- Call `prepareCollaborationServerDocument(live)` once when you create the live room, before `loadRoom`.
- `readCollaborationFormatVersion` is a cheap metadata read, even for incompatible rooms. `readCollaborationDocument` validates content with a full export.
- A failure leaves the snapshot intact. Treat unrecognized decoding errors as damaged data.
- An unseeded room throws `not-initialized`, and missing version data throws `collaboration-format-mismatch`. Create an empty room only when storage confirms none exists.

| Your servers run | Release-specific steps |
| --- | --- |
| 2.17.0 | [Upgrade saved rooms](#upgrade-saved-rooms). Text-only rooms need [their earlier editor](#replace-the-experimental-text-collaboration-api). |
| 2.18.0 to 2.27.0 | [Format 1.4.2.1 steps](#upgrade-rooms-to-format-1421) |
| 2.28.0 to 2.31.0 | [Format 1.5.2.1 steps](#upgrade-rooms-to-format-1521) |
| 2.32.0 or 2.33.0 | [Format 1.5.3.1 steps](#upgrade-rooms-to-format-1531), then [Format 1.5.4.1 steps](#upgrade-rooms-to-format-1541) |
| 2.34.0 to 2.37.0 | [Format 1.5.4.1 steps](#upgrade-rooms-to-format-1541) |

Refuse clients with a different format. A compatible client does not make an older room compatible.

### Upgrade rooms to format 1.4.2.1

Format `docx-collaboration:1.4.2.1` stores each paragraph's text, runs, and formatting as one shared text, so concurrent property edits both survive. Earlier formats refuse to share its rooms.

Add the two server calls that a 2.27.0 server does not make, as [Migrate rooms on a server](#migrate-rooms-on-a-server) describes. A paragraph exported with two `w:pPr` elements opens with the first and keeps the second unchanged.

Undo restores replaced text at the replacement's position, even after another participant types there.

### Upgrade rooms to format 1.5.2.1

Format `docx-collaboration:1.5.2.1` stores tracked insertions, deletions, and moves as attributes of the shared text, so a concurrent decision covers the whole insertion. Sessions no longer refuse these edits with `edit.tracked-foreign-revision-unsupported`. Format `docx-collaboration:1.4.2.1` refuses to share its rooms.

Keep both server calls, and change the browser storage key again.

### Upgrade rooms to format 1.5.3.1

Format `docx-collaboration:1.5.3.1` adds optional records for paragraph placement, undo, and proposed deletions, and keeps the shared schema version. Its conflict rules differ, so `docx-collaboration:1.5.2.1` participants refuse its rooms. Existing rooms keep their format until migrated.

Keep both server calls, and change the browser storage key. Update clients, servers, export workers, and agents together, because your connection check refuses `docx-collaboration:1.5.2.1` clients.

Outside collaboration, rejecting a proposed paragraph break keeps the paragraph before the break, with its `w14:paraId` and `Paragraph.uniqueLocalId`. Automation `Paragraph` objects for the following paragraph stop resolving.

In collaboration, format `docx-collaboration:1.5.3.1` applies these rules:

- Rejecting a proposed paragraph break keeps the preceding paragraph and its text, also during a concurrent undo of that break. The surviving paragraph mark supplies the paragraph properties.
- A proposed paragraph deletion excludes concurrent text that its author has not received. Accepting the deletion keeps that text.
- Undoing a paragraph insertion moves other participants' text into the preceding paragraph, or into the following paragraph when none precedes it.

### Upgrade rooms to format 1.5.4.1

Format `docx-collaboration:1.5.4.1` lets participants edit a shape's fill and outline. When two participants write a fill or an outline of one shape at the same time, each participant shows the first one. Format `docx-collaboration:1.5.3.1` participants lack this rule and could save a shape with two fills, so they refuse these rooms. The shared schema version stays the same.

Keep both server calls, and change the browser storage key. Update clients, servers, export workers, and agents together, because your connection check refuses `docx-collaboration:1.5.3.1` clients.

### Replace the experimental text collaboration API

`createTextCollaboration` is removed. Use `createDocumentCollaboration`, which synchronizes the full document.

| Removed or deprecated | Replacement |
| --- | --- |
| `CreateTextCollaborationOptions`, `TextCollaborationHandle` (removed) | `CreateDocumentCollaborationOptions`, `DocumentCollaborationHandle` |
| `TextCollaborationSession` (deprecated) | `DocumentCollaborationSession` |
| `PROTOCOL_VERSION`, `SCHEMA_VERSION`, `MAX_BASELINE_BYTES` (deprecated; describe the retired factory) | `COLLABORATION_FORMAT_VERSION` |

To move a text-only room:

1. Join it with its earlier editor, wait for synchronization, and save a DOCX. The baseline bytes omit later edits.
2. Seed a full-document room from that DOCX with `createDocumentCollaboration`, under a new room ID and persistence key.
3. Keep the original state and earlier build for recovery.

`readCollaborationDocument` and `migrateCollaborationRoom` cannot read text-only state.

## Upgrade saved rooms

A build that supports a room's recorded format exports a DOCX. The target build seeds a room from that export and checks it before it replaces anything.

| Procedure | When to use it |
| --- | --- |
| [Migrate rooms on a server](#migrate-rooms-on-a-server) | You store rooms and can stop editing. Rooms keep their IDs, storage keys, and links. |
| [Replace rooms with new IDs](#replace-rooms-with-new-ids) | You keep the earlier room available while users recover work. |

Rehearse on copies in a test deployment. Collaboration undo history starts afresh.

### Migrate rooms on a server

The new build provides two byte-in, byte-out functions in `@docx-editor.dev/pro/collaboration`:

| Function | Result |
| --- | --- |
| `collaborationMigrationNeed(state)` | `current`, `earlier-format`, or `later-format`. Only `earlier-format` needs migration. Never open or replace a `later-format` room with this build. |
| `migrateCollaborationRoom({ state, exported, documentId? })` | Seeds a current-format room from the export and checks every XML part, media file, and link target. The check ignores namespace declarations, relationship parts, and renumbered paragraph and `w:id` values. References must keep their targets, and revision IDs must stay unique. Returns `{ ok: true, state, report }`, or `ok: false` with `reason` `check-failed` (plus `report`), `current`, or `later-format`. Omit `documentId` to keep the earlier ID. |

Old replicas can still hold a migrated room's ID. The new servers must call `prepareCollaborationServerDocument` before state loads, as in [Prepare the room document on a server](/docs/2.x/pro/collaboration#prepare-the-room-document-on-a-server). They must also call `checkCollaborationRoomGeneration` in `beforeHandleMessage`, as in [Compact rooms on a server](/docs/2.x/pro/collaboration#compact-rooms-on-a-server). New-build clients then rejoin after `room-generation-changed`, and earlier-build tabs are refused until reloaded.

To migrate the rooms:

1. Ask users with offline edits to reconnect. Edits that never reach the room do not transfer.
2. Stop every server and background job that writes to the rooms, and back up every room.
3. [Export every room with the earlier build](#export-rooms-with-the-earlier-build), and store each export with its state digest.
4. With the new build, [migrate each room](#migrate-each-room) with writes off. If any outcome is not `would-migrate` or `current`, stop. No room has changed.
5. Run it with writes on, and check every result before starting any server.
6. Deploy the new build with both server calls. If your app keeps room updates in browser storage, change the storage key.
7. Start the servers. Test a few rooms with two clients.

The write run is atomic per room, not across all rooms. If it stops, keep the servers stopped and resume, or restore every migrated room from backup. Keep backups and the earlier build until you accept the migration.

#### Export rooms with the earlier build

Install the earlier build in a separate directory, replacing `2.27.0` with the release your servers ran. Node.js 22.18 or later runs the TypeScript files directly:

```bash
mkdir room-export && cd room-export
npm init -y && npm pkg set type=module
npm install @docx-editor.dev/pro@2.27.0 @docx-editor.dev/core@2.27.0 yjs@^13.6.32
```

Export each room and hash the exact state you exported:

```ts
import { createHash } from 'node:crypto';
import * as Y from 'yjs';
import { readCollaborationDocument } from '@docx-editor.dev/pro/collaboration';

export function exportRoom(state: Uint8Array) {
  const room = new Y.Doc();
  try {
    Y.applyUpdate(room, state);
    return {
      exported: readCollaborationDocument(room),
      stateDigest: createHash('sha256').update(state).digest('hex'),
    };
  } finally {
    room.destroy();
  }
}
```

The digest ties the export to the state. Your migration compares digests; `migrateCollaborationRoom` does not. If a room changes after export, export it again.

#### Migrate each room

The following function migrates one room in place. `storage` stands for your storage, and `dryRun` turns writes off:

```ts
import { createHash } from 'node:crypto';
import {
  CollaborationSchemaError,
  collaborationMigrationNeed,
  migrateCollaborationRoom,
} from '@docx-editor.dev/pro/collaboration';

type SavedExport = { exported: Uint8Array; stateDigest: string };

// Loads `state` into a prepared Y.Doc and calls readCollaborationDocument.
declare function validateRoom(state: Uint8Array): void;
declare const storage: {
  readRoom(roomId: string): Promise<Uint8Array>;
  readExport(roomId: string): Promise<SavedExport | null>;
  backUpRoom(roomId: string, state: Uint8Array): Promise<void>;
  writeRoom(roomId: string, state: Uint8Array): Promise<void>; // One atomic write.
};

async function migrateRoom(roomId: string, dryRun: boolean) {
  const state = await storage.readRoom(roomId);
  try {
    const need = collaborationMigrationNeed(state);
    if (need === 'later-format') return need;
    if (need === 'current') {
      // The format check alone does not prove the document opens.
      validateRoom(state); // Throws on failure.
      return 'current';
    }
    const saved = await storage.readExport(roomId);
    if (!saved) return 'no-export';
    const digest = createHash('sha256').update(state).digest('hex');
    if (saved.stateDigest !== digest) return 'stale-export';
    const migrated = await migrateCollaborationRoom({ state, exported: saved.exported });
    if (!migrated.ok) return migrated.reason === 'check-failed' ? 'failed-check' : migrated.reason;
    // Log `report` positions only: `differences` also holds document text.
    if (dryRun) return 'would-migrate';
    await storage.backUpRoom(roomId, state);
    await storage.writeRoom(roomId, migrated.state);
    return 'migrated';
  } catch (error) {
    if (!(error instanceof CollaborationSchemaError)) throw error;
    console.error(roomId, error.code, error.detail);
    return 'error';
  }
}
```

You can rerun the migration after an interruption.

| Outcome | Meaning | What you do |
| --- | --- | --- |
| `migrated`, `would-migrate` | Passed the check. | Review paragraphs in `hiddenAt`. |
| `current` | Already current. | Nothing. |
| `failed-check` | Differs from the export. Unchanged. | Do not finish. Contact support with the report. |
| `no-export` | No export exists. | Export with the earlier build. |
| `stale-export` | Changed after export. | Export again. |
| `later-format` | A later build wrote it. | Serve it with that build. |
| `error` | An input is unusable. Unchanged. | Act on the error code. |

| Error code | Meaning | What you do |
| --- | --- | --- |
| `not-initialized` | No openable document. | Keep it backed up, and drop it from the set. |
| `invalid-document-id` | No usable document ID. | Pass the clients' ID as `documentId`. |
| `invalid-baseline` | Not room state, or the export is not a DOCX. | Read both again, then contact support. |
| A limit code, such as `too-many-nodes` | Export too large for a room. | Contact support with the code. |

| Report field | Meaning |
| --- | --- |
| `differences` | Differences in document order. Read the first, because a missing paragraph shifts later ones. |
| `changedParts` | The XML parts that differ. |
| `hidden` | The count of paragraphs the editor cannot show or edit. They save back unchanged and do not fail the check. |
| `hiddenAt` | The positions of the first 20 hidden paragraphs at most. Use `hidden` for the total. |

Review hidden paragraphs before people edit the room.

#### Migrate rooms stored as update lists

If storage keeps a list of updates, merge it with `Y.mergeUpdates` in the earlier build, and store the result as the only update. Then export and hash those bytes. After the migration, replace the whole list with the migrated state.

#### Plan the migration window

Memory grows with paragraph count. Test your largest rooms, and run one room at a time per worker, with a heap limit. For measurement commands, see the [migration memory benchmark](https://github.com/eigenpal/docx-editor/tree/main/benchmarks/collaboration-server#measure-room-migration-memory).

#### Roll back a migration

1. Preserve unsynchronized client work, then stop the new build's servers and jobs.
2. If people edited the migrated room, export it with the new build. Those edits do not transfer back.
3. Restore the room's backup.
4. Use a fresh browser persistence key. Do not replay updates from the migrated generation.
5. Start the servers with the earlier build.

The [Hocuspocus example migration scripts](https://github.com/eigenpal/docx-editor/tree/main/examples/collaboration-hocuspocus#migrate-saved-rooms) run this procedure with a dry run and keep each backup as `<room>.ydoc.previous`.

### Replace rooms with new IDs

1. Pause editing and background jobs, and let accepted updates finish. Ask users with offline edits to reconnect or save their work.
2. Back up each room. Keep the build that opens the backup, and [export a DOCX](#export-rooms-with-the-earlier-build) with it.
3. Reopen the DOCX and check its content. An export does not repair existing damage.
4. Deploy compatible clients, servers, agents, and workers. Call `migrateCollaborationRoom({ state, exported, documentId })` with the new room ID. If `ok` is false, keep the original room.
5. Store the result under a new storage key and browser persistence key, and route the document link to it. Never copy data or pending updates from the old room.
6. Test the new room with two clients. Keep the old room and backups read-only until you accept the migration.

Once people edit the new room, reconcile its changes before routing users back. Never send its updates to the original room.

## Help users recover

Unsynchronized edits and collaboration undo history do not transfer automatically. Keep the local document available, and offer a DOCX download through `await editor.save()` before reloading, clearing storage, or replacing a session.

| Where compatibility fails | Suggested message | Application action |
| --- | --- | --- |
| A client is refused before synchronization | "This app version cannot join the document. Save your work, then open the compatible version." | Link the compatible deployment. |
| Your server cannot open a saved room | "This document needs a collaboration upgrade. Contact your administrator." | Keep the room and migrate it. |
| An active session reports a mismatch | "Collaboration stopped. Save a copy of your changes." | Preserve local work. |

- `collaboration-format-mismatch`, `protocol-version-mismatch`, and `schema-version-mismatch` mean the formats differ, not which side is older. Choose the message by the failed operation, and stop reconnecting.
- Rejoining uses the room's document and does not merge the saved copy.
- Reconnect a client with offline work to the previous deployment before the final export, or reconcile its DOCX separately. Never replay old queued updates into a new room.
- A thrown mismatch error includes this guide's URL in its `message`. For hook errors, render your own message.

For other failures, see [Recover a diverged replica](/docs/2.x/pro/collaboration#recover-a-diverged-replica).

## Verify a deployment

In a test deployment, confirm:

- Compatible clients join, edit, reconnect, and export.
- Incompatible clients and saved rooms are refused, and rooms stay unchanged.
- Offline work stays recoverable.
- Migrated rooms accept edits from two clients and export the expected document.
- `collaborationMigrationNeed` returns `current` for every room, and `readCollaborationDocument` validates each one.
- An earlier-build tab is refused, and a new-build tab that held the earlier room rejoins after `room-generation-changed`.
