Document objects are proxies that queue operations. Get them through `context.document` inside `runtime.run()`. A `RunCallback<T>` receives a `RequestContext`, and `run()` returns the callback's result.

For runtime setup, see [Runtime and setup](/docs/2.x/editor-api/runtime).

## Load properties in batches

The following example loads paragraphs and two properties in one sync:

```ts
const headings = await runtime.run(async (context) => {
  const paragraphs = context.document.paragraphs;
  paragraphs.load({ select: 'items/text,items/style', top: 100 });
  await context.sync();
  return paragraphs.items.map((paragraph) => ({
    text: paragraph.text,
    style: paragraph.style,
  }));
});
```

Return plain data from the run. `ClientObject.load(option?)` queues reads and returns the same proxy. A navigation getter returns another proxy without loading its properties.

| `LoadOption` form | Meaning |
| --- | --- |
| `load('text')`, `load('text,style')`, `load(['text', 'style'])` | Load named scalar properties |
| `load('items')` | Load collection membership; load item properties in a later sync |
| `load('items/text')`, or `load('text')` on a collection | Load the items and `text` on each item in one sync |
| `{ select: 'items', top: 20, skip: 40 }` | Load a collection window; `top` and `skip` take nonnegative integers |
| `load()` | Load the default selection; prefer explicit names |
| `expand` | Reserved; a nonempty value fails with `InvalidArgument` |

Load paths have these limits:

- Only one level of navigation works. `items/font/bold`, `items/font`, and `font/bold` fail with `InvalidArgument` and name the path in `target`.
- To read font properties, load `font` on each item instead.
- Unknown properties and options also fail.

## Separate dependent writes

Each `sync(): Promise<void>` commits its writes atomically. Await each sync before the next; setters called while a sync waits join the next one. Returning from `run()` does not flush commands, so end with `await context.sync()`.

| Read | Value it reports |
| --- | --- |
| Load on an existing object, in the same sync as a write | The value before the write, except comment and reply content loads, which follow queue order |
| Load on an object that a write in the sync returns | The value after all writes in the sync |
| Load in a later sync | The written value |

The following example loads an inserted range in the insertion sync:

```ts
await runtime.run(async (context) => {
  const inserted = context.document.body.paragraphs.getFirst().insertText('#', 'End');
  inserted.load('text');
  inserted.font.load('italic');
  await context.sync();
});
```

That load runs after the writes commit. If it fails, the writes stay applied, with `innerError.code` `edit.read-after-commit`.

| Operation on an object a pending sync inserts | Result |
| --- | --- |
| Load its properties in the same sync | Reads the value after the writes |
| Edit it, or navigate from it with `getFirst()`, `search()`, or `getCell()` | Fails with `InvalidObjectPath`, and nothing commits. Complete the sync first |
| Read the range that a separate plain-text edit returns | Offsets account for all edits in the same sync |

Atomicity applies per sync, not per run: a later failure does not undo an earlier sync. Prerequisite reads share one revision, and a concurrent edit produces `StaleDocument` without a replay.

## Keep proxies valid

The following example tracks a proxy and adopts it in a later run:

```ts
const paragraph = await runtime.run(async (context) => {
  const first = context.document.paragraphs.getFirst();
  first.load('text');
  await context.sync();
  context.trackedObjects.add(first);
  return first;
});

await runtime.run(paragraph, async (context) => {
  paragraph.load('text');
  await context.sync();
  context.trackedObjects.remove(paragraph);
});
```

| Rule | Detail |
| --- | --- |
| Lifetime | A proxy works across syncs in its run. An untracked proxy becomes invalid when the run ends. |
| Tracking | `TrackedObjects.add()` and `remove()` take one `ClientObject` or an array. Tracking extends lifetime; it does not keep a range stable or prevent deletion. |
| Adoption | `runtime.run(objectOrArray, callback)` adopts tracked objects from completed runs. Adopting before the first run finishes fails with `ObjectInUse`. |
| Removed target | If a run, collaborator, or undo removes the target, the next sync fails with `InvalidObjectPath` and `innerError.code` `edit.stale-target`. Read again. |
| Absent item | Use a null-object accessor such as `getFirstOrNullObject()`, then check `isNullObject` after sync. `getFirst()` on an empty collection fails with `ItemNotFound`. |
| Results | `ClientResult<T>` exposes `isLoaded` and `value`. Reading `value` before its sync throws `ValueNotLoaded`. |
| Disposal | No proxy survives runtime disposal. |

A range keeps the offsets it had when found. A text edit before its end makes it fail with `StaleDocument`. A range across paragraphs also fails when text changes in an intervening paragraph, or a paragraph appears or disappears. For details, see [Refresh ranges after edits](/docs/2.x/editor-api/text-and-ranges#refresh-ranges-after-edits).

## Handle failed batches

Catch both synchronous call failures and rejected syncs. Check `isDocxEditorError(error)`, then branch on `code`, never on message text.

| `DocxEditorErrorCode` | Recovery |
| --- | --- |
| `PropertyNotLoaded` | Load the property and sync before reading |
| `ValueNotLoaded` | Complete the sync that produces the result |
| `InvalidObjectPath` | Sync a pending object, or get a fresh proxy. `edit.stale-target` means the document no longer holds the object |
| `ObjectInUse` | Await the owning run before adopting its tracked objects |
| `InvalidArgument` | Correct the input, property name, location, or target |
| `ResourceLimitExceeded` | Inspect `limit`; reject the file or adjust input budgets |
| `ItemNotFound` | Handle absence, or use a null-object accessor |
| `NotSupported`, `NotImplemented` | Outside the supported subset. Do not retry the same call. Read `innerError.code`, then change the call, mode, target, or content. Nothing changed, except when the editor cannot place a selection: other writes in that sync can already be committed, so read again before you retry |
| `ConflictingChanges` | Read again and split dependent edits into separate syncs |
| `InvalidRequestContext` | Start a new run |
| `RuntimeDisposed` | Create a new runtime |
| `StaleDocument` | Read again and reconsider. With `edit.read-after-commit`, the writes are applied: do not apply them again |
| `DocumentUnavailable` | Wait for the editor to attach a document, then start a new run |
| `PreviewActive` | Commit or discard the open preview |
| `PreviewEnded` | Start a new preview |
| `GeneralException` | Act on `innerError.code`. For `edit.internal-invariant`, or no `innerError`, report the failure with the engine version and do not retry unchanged. See [Diagnostics](/docs/2.x/guides/diagnostics#edit-internal-invariant) |

`DocxEditorError` and `DocxEditorErrorInit` carry `code` and optional `target`, `limit`, `expectedRevision`, and `actualRevision`. On `StaleDocument`, compare the revisions:

| Revisions             | Meaning                                                         |
| --------------------- | --------------------------------------------------------------- |
| Different             | Another writer changed the document                             |
| Equal                 | A range moved in an earlier sync, or its history record expired |
| No `expectedRevision` | The batch was read-only                                         |

Never disable change tracking to bypass a refusal. For a per-suggestion recovery loop, see the [server agent guide](https://github.com/eigenpal/docx-editor/blob/main/packages/editor-api/OFFICE_JS_GUIDE.md).

### Detect committed writes after an error

`error.debugInfo` has the Office.js `OfficeExtension.DebugInfo` shape. `errorLocation` names the refused call, or the later call of two that conflict. `innerError` holds a stable code and a hint with no document content:

```ts
import { isDocxEditorError } from '@docx-editor.dev/editor-api';

try {
  await context.sync();
} catch (error) {
  if (!isDocxEditorError(error)) throw error;
  const reason = error.debugInfo.innerError;
  if (reason?.code === 'edit.read-after-commit') {
    // The writes are applied. Read again, and do not apply them a second time.
  } else if (reason) {
    feedback.push(`${reason.code}: ${reason.message}`);
  }
}
```

For every code, see [Diagnostics](/docs/2.x/guides/diagnostics). To record anonymous refusal events, see [Server agents](/docs/2.x/telemetry/agents).

## Limits

- Text and formatting writes in one sync must target one story: the main body, a header, a footer, a note, or a text box. Otherwise they fail with `ConflictingChanges`. Reads can mix stories.
- Bookmark removal is the exception: `Document.deleteBookmark()` and `Bookmark.delete()` can share a sync with writes to another story. Inserting a bookmark can move a same-name bookmark from another story.
- Linked headers or footers can share content. Read again before a dependent edit through another section.
- Run each row or column addition or deletion, and each `insertBreak()` other than `Line`, in its own sync.
- Plain-text edits in one paragraph can batch. Mixing them with formatting, hyperlinks, or structural writes in that paragraph refuses.
- Different levels of one list can share a sync; competing aliases for one level conflict.
- Keep field result updates apart from layout-changing writes.
- The ranges that `Paragraph.split()` returns accept `items/` paths, `top`, and `skip` after the split's sync. Before it, such a load fails with `NotImplemented`.
- For tracked structural edits, see [Propose several structural edits in one run](/docs/2.x/editor-api/revisions#propose-several-structural-edits-in-one-run).
