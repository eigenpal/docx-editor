Use `Document.changeTrackingMode` to create tracked text edits and `RevisionCollection` to review them. To accept or reject multiple changes, use `RevisionCollection.resolve()` for an API batch or the editor command for changes shown by a filter. To attribute pending changes to another author, use `RevisionCollection.setAuthor()` or the `setReviewChangesAuthor` editor command.

Create a `runtime` with [Runtime and setup](/docs/2.x/editor-api/runtime). Use `context` and document proxies inside `runtime.run()`.

## Create a tracked replacement

Configure a nonempty `author` when creating the runtime. For browser tracked writes, install the Pro review module on an editable editor. Then enable `TrackMineOnly` and use an ordinary range edit:

```ts
await runtime.run(async (context) => {
  const matches = context.document.body.search('within 7 days', {
    matchCase: true,
  });
  matches.load('items');
  await context.sync();
  if (matches.items.length !== 1) throw new Error('Choose one deadline');
  context.document.changeTrackingMode = 'TrackMineOnly';
  matches.items[0]!.insertText('within 30 days', 'Replace');
  await context.sync();
});
```

Use `insertText(text, 'Before' | 'After')` for insertion suggestions. Use `range.delete()` or `range.clear()` for deletion suggestions. Inserted ranges require sync before dependent use. Mode assignments and edits commit together; a failed batch preserves the previous mode and document.

| `ChangeTrackingMode` value | Runtime behavior |
| --- | --- |
| `Off` | Initial mode; ordinary permanent edits |
| `TrackMineOnly` | Text and property tracking for this runtime with an explicit author; browser writes require the Pro review module |
| `TrackAll` | Fails with `NotSupported` |

The runtime's tracking setting does not change the browser editor UI mode. Read `document.changeTrackingMode` only after loading it. The mode persists across runs on that runtime. It does not change peers' tracking settings or save a document-wide tracking policy. Set `Off` explicitly only when your application intends permanent edits.

## Supported tracked edits

`TrackMineOnly` supports these edits:

| Edit | Supported behavior |
| --- | --- |
| Range text | Insert, replace, or delete text; adjacent sibling paragraphs work outside collaboration |
| Font and paragraph formatting | Record property revisions, including paragraph styles |
| Paragraph insertion | Track text and paragraph marks; reject removes both |
| Lists | Track creation, membership, and level changes; configure newly proposed definitions |
| Tables | Track complete insertion, cell values, row additions, and partial row deletions |
| Content controls | Wrap nonempty ordinary text in `PlainText`, `RichText`, or `DatePicker` controls outside collaboration |

Tracked ranges refuse table and wrapper boundaries. Collaborative tracked ranges must remain within one paragraph. Targets that touch foreign pending revisions refuse. Insertions can continue the runtime author's text, paragraph, and formatting proposals.

Appends can follow the author's pending deletion at the paragraph tail. Within one paragraph, a tracked replacement or deletion can start where the author's own pending inserted text ends, and it stays a separate decision. Other boundaries with the author's pending changes refuse: a deletion beside their deletion, or directly before their insertion, would review as one decision with it. A replacement or deletion that covers the author's pending text, or touches another author's change, also refuses. Structural and move revisions also block continuation.

A pending row insertion or deletion blocks tracked text edits throughout that row, including nested tables. An author can configure a complete proposed table while it has no foreign revisions. Existing table properties and columns require permanent edits. Tracked table and cell value replacement refuse in collaboration. See [Tables and cells](/docs/2.x/editor-api/tables#row-suggestions) for row deletion limits.

Accept keeps a proposed content control. Reject restores the original formatted text. The author can set the pending control's `tag` and `title`. Empty ranges, existing review markup, and other control structure changes refuse.

Established list definitions, pictures, page setup, and unsupported structural edits refuse. Comments and supported revision decisions remain available.

Never turn tracking off automatically to make an unsupported operation succeed. Report the limit or ask your application to choose a separately authorized permanent edit. For a multi-stage review, each successful sync becomes a separately committed suggestion. A later refusal does not roll back earlier suggestions.

## Choose the revision text view

The runtime option `revisionTextView` affects ordinary text loads and search. `allMarkup` is the default. `original` retains pending deletions and hides pending insertions. This is a DocxEditor host option, not a Word document-model property. It does not accept or reject revisions.

Use plain text and explicit revision information when preparing a model prompt. Do not pass live proxies into a model or job queue. See [Runtime and setup](/docs/2.x/editor-api/runtime).

## Inspect revisions by story

`Document.revisions` addresses the main story. `Body.revisions` addresses that body's story, including a header, footer, or note. It never merges all stories into one collection.

Load collection membership, then load `author`, `date`, and `type`:

```ts
const pending = await runtime.run(async (context) => {
  const revisions = context.document.revisions;
  revisions.load('items');
  await context.sync();
  for (const revision of revisions.items) {
    revision.load(['author', 'date', 'type']);
  }
  await context.sync();
  return revisions.items.map((revision) => ({
    author: revision.author,
    date: revision.date?.toISOString() ?? null,
    type: revision.type,
  }));
});
```

`Revision.date` is `Date | null`; narrow missing or invalid dates before using date methods. `Revision.type` uses the exported `RevisionType` vocabulary. `Revision.range` returns a range for the addressed revision. Resolve the range before reading or selecting its content. `RevisionCollection` exposes `items`, `resolve()`, `setAuthor()`, `acceptAll()`, and `rejectAll()`; it has no first-item accessor.

## Resolve a batch of changes

Use `RevisionCollection.resolve(action, revisions?)` to accept or reject supported changes in one story. Pass `'accept'` to keep the changes or `'reject'` to undo them. Unsupported changes remain pending.

API batches don't inherit editor filters. Pass revision objects from the same request context and story to select changes. For example, accept Ada's changes:

```ts
await runtime.run(async (context) => {
  const revisions = context.document.revisions;
  revisions.load('items');
  await context.sync();
  for (const revision of revisions.items) {
    revision.load('author');
  }
  await context.sync();

  const selected = revisions.items.filter((revision) => revision.author === 'Ada');
  const result = revisions.resolve('accept', selected);
  await context.sync();

  const { resolved, skipped, remaining } = result.value;
  console.log({ resolved: resolved.length, skipped, remaining });
});
```

Read `result.value` after `context.sync()`. Changes commit in one transaction and one undo step. Browser writes require the Pro review module and an editable document.

To process the whole story, omit the selection. This includes complete tracked rows and reports unsupported changes omitted from `items`:

```ts
await runtime.run(async (context) => {
  const result = context.document.revisions.resolve('reject');
  await context.sync();
  for (const skipped of result.value.skipped) {
    console.log(skipped.revision?.author, skipped.reason);
  }
});
```

Keep `resolve()` as the only write in its sync batch; reads can share the batch. Use a separate sync for each story. Protection, content control locks, and collaboration permissions still apply. If the transaction fails, no changes commit and the result remains unloaded.

### Interpret the result

| Field | Meaning |
| --- | --- |
| `resolved` | Resolved decisions, with their key, author, part name, and revision kind. |
| `skipped` | Requested decisions left pending, with a key, reason, and `revision` metadata when known. |
| `remaining` | Number of pending decisions in the story, including excluded and unsupported changes. |

A decision can contain several XML markers, such as split deletion fragments. A replacement keeps its deletion and addition decisions separate. A successful batch can leave changes pending:

| Skip reason | Next step |
| --- | --- |
| `unsupported-revision` | Resolve the unsupported structure in Word. Independent supported changes can still resolve. |
| `incomplete-group` | Review and select all related decisions together. |
| `retained-structure` | A row remains to preserve nested table content. Other selected text changes may have applied; inspect the remaining decision. |
| `unknown-revision` | Reload the collection; the target no longer exists. |

Nested changes, move pairs, tracked rows, and paragraph marks with property changes can form inseparable groups. If a group contains an excluded or unsupported decision, the batch skips the group, even if the action could preserve part of it. It doesn't expand your selection. A `retained-structure` result is different: supported text changes in the selected row can resolve while its structural marker stays pending to preserve the nested table.

Pass an empty array to select nothing. Duplicate objects resolve once; stale objects produce `unknown-revision`. Objects from another context or story fail validation.

Use revision objects instead of raw OOXML `w:id` values, which Word can reuse. Treat result keys as opaque identifiers for the open document. Reload revisions after saving and reopening a file.

## Resolve changes shown in the editor

The editor's bulk controls honor author visibility and the tracked-changes filter, including offscreen changes in supported stories. Mounted cards and activation exclusions don't affect the selection. Supported changes resolve in one undo step; unsupported changes remain pending.

For example, accept changes shown by an author filter:

```ts
editor.setTrackedChangesFilter((revision) => revision.author === 'Ada');
const result = editor.exec({
  type: 'resolveAllReviewChanges',
  action: 'accept',
});
if (result.ok) {
  console.log(result.revisions);
}
```

To select an explicit batch, pass `keys` from `editor.getReviewItems()`. Keys override the active filter:

```ts
const keys = editor
  .getReviewItems({ placement: false })
  .filter((item) => item.kind === 'revision' && item.author === 'Ada')
  .map((item) => item.key);

const result = editor.exec({
  type: 'resolveAllReviewChanges',
  action: 'reject',
  keys,
});
```

To include all authors across supported stories, pass `scope: 'document'`. To require every selected change to resolve, pass `unsupported: 'fail'`. The defaults are `scope: 'visible'` and `unsupported: 'skip'`.

The result has the same fields as an API batch; `remaining` counts pending decisions across the document, including hidden changes. If no eligible changes exist, `editor.can()` returns a refusal and `editor.exec()` adds no undo step.

## Change the author of tracked changes

A change can belong to a different person than the one who made it. For example, an agent proposes edits, and a reviewer adopts them while tracking stays on. Change the author to the reviewer. The changes stay pending, so another reviewer can still accept or reject them.

`RevisionCollection.setAuthor(author, selection?, options?)` changes `w:author` on the selected changes in one story. Pass one of these as `selection`:

- `{ authors }` selects every change those authors made.
- An array of `Revision` objects selects those changes.
- Nothing selects every change in the story, by every author.

To also record a new date, pass `options.date`. Otherwise each change keeps its own date. For example, give the agent's changes to the reviewer:

```ts
await runtime.run(async (context) => {
  const result = context.document.revisions.setAuthor(
    'Ada Lovelace',
    { authors: ['Contract agent'] },
    { date: new Date() }
  );
  await context.sync();

  console.log(result.value.updated.length, result.value.skipped);
});
```

To select individual changes, load them first and pass the objects:

```ts
await runtime.run(async (context) => {
  const revisions = context.document.revisions;
  revisions.load('items');
  await context.sync();
  for (const revision of revisions.items) {
    revision.load(['author', 'type']);
  }
  await context.sync();

  const insertions = revisions.items.filter(
    (item) => item.author === 'Contract agent' && item.type === 'Insert'
  );
  revisions.setAuthor('Ada Lovelace', insertions);
  await context.sync();
});
```

Omitting a selection includes structural changes, such as tracked rows, that `items` omits. It also takes the changes of human authors, so pass a selection when you mean only some authors. An empty array selects nothing.

The revision objects you pass stay valid. After the sync, load `author` again to read the new value. Selection rules and transactions match `resolve()`. Browser writes require the Pro review module and an editable document.

| Error code | Cause |
| --- | --- |
| `InvalidArgument` | A blank author, an invalid date or selection, or a revision object from another request context. `setAuthor()` throws before it queues anything. |
| `ConflictingChanges` | `setAuthor()` shares its sync batch with another write. Keep it as the only write in its batch. |
| `GeneralException` | Document protection refuses the change. |
| `NotSupported` | A browser runtime has no Pro review module. |

The result reports each selected change:

| Field | Meaning |
| --- | --- |
| `updated` | Changes that have the new author. `key` and `author` describe each change after the update; `previousKey` and `previousAuthor` describe it before. |
| `skipped` | Requested changes that kept their author, with a key and a reason. |

| Skip reason            | Next step                                                        |
| ---------------------- | ---------------------------------------------------------------- |
| `unknown-revision`     | Reload the collection; the target no longer exists.              |
| `unsupported-revision` | The change has no author to change, such as a table grid record. |

Document protection for tracked changes refuses author changes, because that protection keeps each change attributed to the person who made it. Read-only and comments-only protection refuse it too.

### Change authors in the editor

To change the author of changes in the editor, run the `setReviewChangesAuthor` command. It selects changes by exact `keys`, or by `scope` narrowed by `authors`. These two selections exclude each other. `unsupported` works as it does in `resolveAllReviewChanges`. Without `author`, it records the editor's `author`, so a reviewer adopts the changes as their own. It runs in one undo step:

```ts
const result = editor.exec({
  type: 'setReviewChangesAuthor',
  authors: ['Contract agent'],
  date: new Date().toISOString(),
});
if (result.ok) {
  console.log(result.revisionAuthors);
}
```

Without `keys`, the command selects the changes shown by the active filters, or every change with `scope: 'document'`. `authors` narrows that selection and matches `w:author` exactly. With the default `scope: 'visible'`, an author that a filter hides selects nothing, so pass `scope: 'document'` to include hidden authors. `date` is an ISO 8601 string, because editor commands carry plain data; `setAuthor()` and `adopt()` take a `Date`.

To select changes by the `w:id` values your application stored, match them to the revision addresses of review items, and pass their keys:

```ts
const ids: readonly string[] = storedRevisionIds;
const keys = editor
  .getReviewItems({ placement: false })
  .filter(
    (entry) =>
      entry.kind === 'revision' && entry.item.addresses.some((address) => ids.includes(address.id))
  )
  .map((entry) => entry.key);
editor.exec({ type: 'setReviewChangesAuthor', keys });
```

A `w:id` can repeat in a document, so prefer keys while the document stays open.

Review keys include the author and the date, so an updated change gets a new key. Use `revisionAuthors.updated` to map each `previousKey` to its new `key`. An active review card stays active. If every selected change already has the author and date, the command succeeds with `changed: false` and adds no undo step. In that case `previousKey` equals `key`.

In React and Vue, `useReview().adopt(items)` runs this command for review items. See [Adopt suggestions as your own](/docs/2.x/pro/tracked-changes#adopt-suggestions-as-your-own).

A refused command returns one of these codes and changes nothing:

| Code | Cause |
| --- | --- |
| `invalidArgs` | A blank author, no author on the command or the editor, an invalid date, an invalid selection, or `keys` with `scope` or `authors`. |
| `locked` | The document is open for viewing, or document protection refuses the change. |
| `notFound` | No selected change exists. |
| `unsupported` | No Pro review module, a selection of records with no author, or a skipped change with `unsupported: 'fail'`. |

If a new author would give one change the identity of another pending change, the editor gives the changed revision a new `w:id`. The two changes stay separate decisions.

## Require every change to resolve

Use `Revision.accept()` or `Revision.reject()` for one supported revision. Use `RevisionCollection.acceptAll()` or `rejectAll()` for a strict story-wide batch:

```ts
await runtime.run(async (context) => {
  context.document.revisions.acceptAll();
  await context.sync();
});
```

These collection methods ignore editor filters and fail the entire sync if any revision is unsupported. They include complete tracked rows omitted from `items`. An empty collection succeeds and keeps document content unchanged.

Malformed content revision wrappers refuse resolution and retain their content. This includes `w:ins` or `w:del` wrappers containing paragraphs.

If a strict batch fails with `NotImplemented`, use `resolve()` to process supported changes and report what remains. For `StaleDocument`, start a fresh run and reload revisions before deciding again.

### Update existing integrations

Existing `acceptAll()` and `rejectAll()` calls keep their behavior. To support partial batches or an explicit selection, use `resolve()`.

The editor's **Accept all changes shown** and **Reject all changes shown** controls honor filters and skip unsupported groups. To keep the previous editor command behavior, pass `scope: 'document'` and `unsupported: 'fail'`.
