Comments anchor discussion to document content. To propose text edits, use [Tracked changes](/docs/2.x/editor-api/revisions).

## Create a comment and reply

Create the runtime with a nonempty `author`. The following example comments on a unique phrase and replies:

```ts
await runtime.run(async (context) => {
  const matches = context.document.body.search('Payment is due');
  matches.load('items');
  await context.sync();
  if (matches.items.length !== 1) throw new Error('Choose one payment clause');
  const comment = matches.items[0]!.insertComment('Confirm the payment deadline.');
  await context.sync();
  comment.reply('Check the signed order form.');
  await context.sync();
});
```

`insertComment()` returns a `Comment`, and a collapsed range creates a point comment. `reply()` returns a `CommentReply`. Sync before dependent work on either.

Browser writes also require the Pro review module and an editable document. Server review uses the EigenPal Pro License. No capability flag covers comment writes, so handle errors from the call or `sync()`.

## Read threads

The following example loads thread properties after membership:

```ts
const threads = await runtime.run(async (context) => {
  const comments = context.document.comments;
  comments.load('items');
  await context.sync();
  for (const c of comments.items) c.load(['id', 'authorName', 'creationDate', 'text', 'resolved']);
  await context.sync();
  return comments.items.map((c) => ({
    id: c.id,
    author: c.authorName,
    date: c.creationDate?.toISOString() ?? null,
    text: c.text,
    resolved: c.resolved,
  }));
});
```

| Member | Behavior |
| --- | --- |
| `Document.comments` | Comments anchored in the main body story only |
| `Body.getComments()` | Comments in that body story |
| `authorName`, `id` | On comments and replies; author names can repeat |
| `creationDate` | `Date \| null`; missing or invalid dates return `null`. New comments record the time to the second |
| `text` | Read-only DocxEditor extension; body replacement is unavailable |
| `Comment.replies` | `CommentReplyCollection` in document order; load `items`, then reply properties |
| `Comment.getRange()` | The anchored range; resolve it before reading or selecting |

On an empty `CommentCollection` or `CommentReplyCollection`, `getFirst()` fails with `ItemNotFound`.

## Resolve or delete threads

| Call                       | Effect                                              |
| -------------------------- | --------------------------------------------------- |
| `comment.resolved = true`  | Resolves the thread and keeps its text and replies  |
| `comment.resolved = false` | Reopens the thread                                  |
| `Comment.delete()`         | Removes the thread, its replies, and its anchors    |
| `CommentReply.delete()`    | Removes one reply and keeps its parent and siblings |

Deletions queued in one sync form one atomic batch, and one browser undo step. Deleted targets become invalid.

## Limits

- Comment creation and replies require a nonempty `author`; the API does not supply an account identity.
- Empty comment text and ranges that cross table cells refuse.
- `Document.comments` does not combine headers, footers, notes, or text boxes.
- An incomplete deletion scan leaves the whole batch unchanged. Mixed thread and reply deletions keep their queue order.
- Saving removes recognized empty comment parts. It does not remove other document metadata.
