`@docx-editor.dev/agents` gives a model's tool calls somewhere to land. You define the tools — you own the schema, the wording and the refusal behavior — and each one does its work inside a `run` block against the document.

```bash
npm install @docx-editor.dev/agents
```

<Steps>
<Step>

## Open the document

On a server, from bytes. Nothing here needs a browser.

```ts
import { DocxEditor } from '@docx-editor.dev/agents';

const runtime = await DocxEditor.createServer(bytes, { author: 'Assistant' });
```

In a page instead, hand it the editor the host already created — from `@docx-editor.dev/react`, `@docx-editor.dev/vue`, or a plain page — and edits land in the open document with the reader's undo stack intact:

```ts
import { DocxEditor } from '@docx-editor.dev/agents/browser';

const runtime = DocxEditor.createBrowser(editor);
```

Everything below is identical either way. The one difference: only the server runtime has `save()`, because in a page the host already owns saving.

</Step>
<Step>

## Write the tools you want the model to have

Two, to start: one that reads and one that edits. Each is an ordinary function over the runtime, and the schema you hand your model is yours to write.

```ts
/** Read the document as numbered paragraphs, so the model can point at one. */
async function readDocument(): Promise<string> {
  return runtime.run(async (context) => {
    const paragraphs = context.document.body.paragraphs;
    paragraphs.load('text');
    await context.sync(); //  reads are declared, then one round trip answers them

    return paragraphs.items.map((p, index) => `[${index}] ${p.text}`).join('\n');
  });
}

/** Replace every occurrence of a phrase. One batch: all of it, or none of it. */
async function replaceText(find: string, replaceWith: string): Promise<number> {
  return runtime.run(async (context) => {
    const matches = context.document.body.search(find, { matchCase: true });
    matches.load();
    await context.sync();

    for (const match of matches.items) match.insertText(replaceWith, 'Replace');
    await context.sync();
    return matches.items.length;
  });
}
```

</Step>
<Step>

## Run the loop

Hand your model the schemas, dispatch what it asks for, feed the results back. This is provider-agnostic — any function-calling API works, because the tools are just functions.

```ts
const TOOLS = {
  read_document: {
    description: 'Read the document as numbered paragraphs.',
    parameters: { type: 'object', properties: {} },
  },
  replace_text: {
    description: 'Replace every occurrence of a phrase.',
    parameters: {
      type: 'object',
      properties: { find: { type: 'string' }, replaceWith: { type: 'string' } },
      required: ['find', 'replaceWith'],
    },
  },
} as const;

async function dispatch(name: string, args: Record<string, unknown>): Promise<string> {
  switch (name) {
    case 'read_document':
      return readDocument();
    case 'replace_text':
      return `replaced ${await replaceText(String(args.find), String(args.replaceWith))}`;
    default:
      // A refusal is a result the model can act on, not an exception it never sees.
      return `no such tool: ${name}`;
  }
}
```

</Step>
<Step>

## Save, and release the document

```ts
try {
  // …your tool loop…
  await writeFile('reviewed.docx', await runtime.save()); //  server runtime only
} finally {
  runtime.dispose(); //  every later run or save fails instead of reaching a freed host
}
```

</Step>
</Steps>

## Why the tools are yours

Earlier versions of this package shipped a fixed tool catalog, an MCP server and a chat UI. They are gone, because a tool schema is a decision about your model's interface — which operations to expose, how to describe them, what a refusal should say — and it belongs in the application that owns the model. What remains is the layer underneath, which is the part that is hard: batching, declared reads, atomic writes, and a document that ends up valid.

If you were using those surfaces, [the migration guide](/docs/1.x/agents/migration) maps every removed call.
